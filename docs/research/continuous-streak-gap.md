# 连续输入那一档：隔多久没输入就归零

问的是「连续用了多久」这个数，隔多久没输入它就归零。
2026-10-21 在本机量了两件事：这个数的阈值是多少，
以及它被拿去当触发条件之后出了什么症状。

**结论（2026-10-21 所有者定夺）：倒计时和触发不再看这个数。**
那一段改按现实时间走。这个数现在只答「人是不是离开了」，
而且**只在挥散过之后**才问。机制在
[`../design/detection.md`](../design/detection.md)「倒计时和触发按现实时间走」那一节。

## 怎么量的

产品带 `--streak 999999` 起（那条线推到 999999 秒，不会触发），
量具 `run.cmd tray` 读托盘菜单第 0 项。

那一项是「下次休息还有多久」（`Scheduler.BreakLeftMs`），
换算：`连续输入 = activityTimeoutMin × 60 − 那一项显示的秒数`。

**量具自己那一下鼠标移动算进了输入** —— 它要点托盘图标。
所以每次读数里都带着那一下，读数偏大。它不影响「归零」这个判据。

## 实测结果

**改之前（60 秒）**，静置 70 秒：

| 时刻 | 托盘第 0 项 | 连续输入 |
| --- | --- | --- |
| 07:40:41 | 「下次休息还有 24:47」 | 13 秒 |
| 07:41:57 | 「下次休息还有 24:56」 | **4 秒** |

**中间那一版（5 分钟）**，静置 76 秒 —— **那一版已弃用**，
读数留在下面是因为它量过：

| 时刻 | 托盘第 0 项 | 连续输入 |
| --- | --- | --- |
| 08:10:11 | 「下次休息还有 24:45」 | 15 秒 |
| 08:11:27 | 「下次休息还有 23:29」 | **91 秒** |

15 + 76 = 91。断档不再清零。

## 症状：五小时零次提醒

桌面上那一份导出版（2026-10-21 02:24 导出）从 02:27 跑到 07:26：

| 证据 | 读数 |
| --- | --- |
| 应用日志里的「淡入」 | 一条都没有 |
| 休息记录 | 零条（`history.jsonc` 当天没有新记录） |
| 按 Esc 时程序答的 | 「遮罩 0 扇」 |

那条线是 25 分钟（`activityTimeoutMin: 25`）。
60 秒的归零阈值下，一次日常的停手（读代码、想问题、起身倒水）就把它断掉，
25 分钟于是永远攒不满。

## 改之后的实测（2026-10-21 08:47）

桌面上那一份（08:46 导出的，284,558,168 字节）带 `--streak 3` 起 ——
那条线推到 3 秒。日志里那一行：

```
08:47:14.716 app  目录=…\.tmp\keeper-verify2 设置读=通（OK）连续 25 分钟提醒一次
08:47:18.068 app  淡入：1 块屏，这一段已经走了 3 秒，连续已经用了 3 秒，静了 3 秒才落进来
08:47:24.020 app  退出
```

起 3.35 秒之后抬 —— 走的是现实时间那一段（3 秒），不是「连续输入攒了多久」。
同一发里编辑器版（`--streak 3 --seconds 10`）读到的也是同一句。

**判据四条的读数**（打包文档第 7 步，对桌面上那一份量的）：
exit 0、stderr 0 字节、日志里有 `托盘：起挂 NIM_ADD=True` 和 `钩子装上了`、
最后一行是 `退出`、桌面上 `Keeper*` 文件 1 个。

## 为什么不再拿它当触发条件

- 60 秒太紧：日常停手就断，触发攒不满（上表）。
- 改成 5 分钟也只盖住日常停手 —— 而「这一段该有多长」这件事
  本来就不该由「人有没有在打字」决定（5 分钟那一版的读数在上面）。
- 2026-10-21 所有者定夺：**删掉这个连续输入跟倒计时的任何关联**，
  而且「连续输入」只在第一次主动挥散之后才开始计算。

所以触发条件改成「这一段从哪一刻起算，到哪一刻满」—— 现实时间。
这一段的起点记在 `Scheduler.SegmentStartMs`。

## 这个数现在答什么

**「人是不是离开了」。** 休息延迟那个欠账在离开够久的时候清零，
下一次回到序列的第一格。没挥散过的时候压根不看它
（没有欠账，也就没有「离开」这一说）。

60 秒这个门槛是所有者定的，**不动**。
