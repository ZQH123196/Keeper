# 桌面层与那扇窗：从进程外量回来的实测结果

这一族是 Windows 的桌面层和引擎那扇窗自己的行为，多数由**另一个进程**验的。合起来解释了「挂进壁纸」「置顶那一位」「每像素透明」这几件事为什么不能照直觉办。

**条数不抄在标题里**（手抄的计数过期过两次）。下面那批是 2026-09-28 补的。上一轮删表的时候说「实测结果已在证据库里」，实际是
**大部分在、那一批不在** —— 而 `src/` 下指着它们的指针有三十几处，其中两条连着契约
（那两处当时写着「置顶那条不许赋引擎旗标」和「挂进壁纸站得住」，指着一个还没有这一发的去处）。
现在补齐，并且分成两个读者位置：**规矩**在 `CODING_STANDARDS.md`，**这些实测结果**在这儿。
由它们定下来的取向都在 **ADR-0003** 那一张里，各占一节（落定那一发 / 鼠标桥默认不喂 / 穿透走引擎旗标）。原来那些取向各是一张独立的卡，2026-09-29 合成了那一张。

- **`SetParent` 进 `SHELLDLL_DefView` 站得住，而且回得去同一个像素**：从 C# 把引擎那扇窗挂进壁纸
  （这台机器的形状是 DefView 直接挂在 `Progman` 底下，没有 `WorkerW` sibling）、改成 `WS_CHILD`
  之后，~1.6 秒里四次问「爹还是不是那一扇」都不掉，跨过 70+ 帧渲染、跨过引擎自己改 `Size` /
  `Position` / `Title`；`SetParent(NULL)` 加还原那两个样式字，回到原来那个像素。挂进去之后
  `WindowFromPoint` 在我们那块矩形的中心回的就是这扇窗自己（`hit == hwnd`，根是 `Progman`）——
  日历那条桥的闸门因此可以按 hwnd 精确开，不必退到「归壁纸层就行」。(量于 09-24、09-26)
- **样式位要一次设完，之后不碰**：唯一那一发读到「爹掉了」的观察，出自设完 `always_on_top`
  又去改别的东西（标题）；所以置顶在别的一切之前设完。之后只有落定那一处例外，而它改的也不是
  样式位本身，见下面 `HWND_NOTOPMOST` 那一条。(量于 09-24)
- **引擎的 `AlwaysOnTop` 赋值会把窗整个藏掉，两个方向都一样**：落定那一段原来跑
  `AlwaysOnTop = false`，读到的是赋值后 16 毫秒 `GetWindowLong(GWL_STYLE)` 里 `POPUP` 而
  **`WS_VISIBLE` 没了**、`IsWindowVisible` false、中心点归别人 —— 而 `Window.IsVisible()` 照样答
  true；**赋成它本来就有的 true 也一样藏**。外部那份实测结果（「把窗插到非置顶栈的底」）是同一件事
  从外面看：藏起来的窗仍在 z 序里，所以 `SetWindowPos(HWND_TOP)` 报「举回顶上=True」什么也没修好。
  落定改成走一发 `SetWindowPos(hwnd, HWND_NOTOPMOST, …|SWP_NOACTIVATE)`，那本来就是「非置顶栈顶」；
  延迟举起和它追的那 1-3 帧排序一起删了 —— 那一手追的是一个误诊。(量于 09-25)
- **`ScreenGetScale()` 在 125% 的屏上报 1**：引擎不跟系统缩放放字。`ScreenGetDpi(0)` 同一块屏报
  120，`GetDpiForWindow` 也报 120，所以日历那根「再小就读不出来」的像素下限和 `textScalePercent`
  乘的都是 `dpi/96`；而**占屏那几档比例不乘**（屏高本来就是物理像素，125% 上「占多少」和 100%
  是同一个数，见 `docs/research/calendar-and-fader-geometry.md` 里遮罩那四组比例那一条）。别拿 `ScreenGetScale` 当缩放实测结果。(量于 09-25、09-26)
- **引擎自己的主循环泵会叫到我们自己 `RegisterClassEx` 的窗的 WndProc**：托盘那扇 0×0 的
  `WS_POPUP` 开在**主线程**上，没有自己的线程也没有自己的 `GetMessage` 循环。2026-09-25 由
  **另一个进程**验的：`PostMessage(hwnd, WM_USER+1, id, WM_LBUTTONUP)` 从 PowerShell 递进来，应用印
  `托盘：回调进来了 左键松开`，淡入 0.1 秒之后起来。两条代价同一次量到：`TrackPopupMenu` 是模态的，
  菜单开着那 14.9 秒里 `_Process` 不跑（当时举着的一段淡入跟着冻住）；而 `SetForegroundWindow` 之后
  合成投递的方向键叫不动那扇 `#32768`（注入的 HOME/DOWN/END 一次没挪高亮，真点进那个矩形才动）。
  (量于 09-25)
- **进程内抓屏要 `DisplayServer.ScreenGetImageRect`**：它和引擎自己的坐标口径一致；外部那份
  `CopyFromScreen` 拍同一扇窗差 1.25 倍，还拍到别人的窗。要「这扇窗自己渲染的那张纹理」则走
  `GetWindow().GetTexture().GetImage()`（那条在 `docs/research/probe-and-criteria-pitfalls.md`）。(量于 09-25)

## 认桌面层的那一发的三条退路（用错不报错）

`DesktopLayer.Look()` 一次把三扇都找出来（`Progman` / `SHELLDLL_DefView` / 托管着 DefView 的 `WorkerW`），
而 `DesktopLayer.Find()` 的 `Parent` 是从那三者里挑一个当爹，**顺序是 DefView → 托管它的 WorkerW → Progman**。
这台机器上的形状是 **DefView 直接挂在 Progman 底下、没有 WorkerW sibling**，
所以那一次 WorkerW 枚举回来是 0，实测结果里印的 `workerw=0x0` 就是这么来的。

**要 DefView 本身的那两处不能用 `Find()`**：桌面图标层（`SysListView32`）是 DefView 的**子窗**，
拿 WorkerW 去 `FindWindowEx` 找不到；`WallpaperHitTest` 那一发是 `SetParent` 进 DefView，
挂进 Progman 是另一件事，而**日志行一模一样**。**用错不报错，它安静地量成另一件事。**
那两处走 `Look().DefView`。正文在 `src/DesktopLayer.cs` 里 `Find` / `Look` 那两段。

`Wallpaper.Refresh` 那一发还是 `Read(0)`，也就是**只问主屏**；日历那侧走的是 `Wallpaper.Read(screen)`，

副屏上是轮播还是静态、路径怎么问，这台机器没量过，所以现在答不了。要走的那一条在
`.scratch/keeper-debt/issues/10-wallpaper-carousel-branch.md`。
（`refreshTimer` 那一发每秒问两次路径和文件时间这件事本身是**测量程序/轮询的形状，不是产品的形状**。）

## 图标层在上面还是在下面：这两件事在 DefView 的子窗堆里只能要一个（量于 10-08）

`SHELLDLL_DefView` 的子窗堆只有两个位置可去，**摆上摆下各量一次，同一扇窗、同一份内容**：

| 位置 | z 序（索引 0 = 最上面） | 屏上量到的 |
| --- | --- | --- |
| 图标层之下 | `[0]SysListView32←图标层 [1]Engine←我们` | **整块什么都没有**，只剩壁纸和图标 |
| 图标层之上 | `[0]Engine←我们 [1]SysListView32←图标层` | **日历整张画出来**（月、星期、农历、备注都在） |

两档的**内容和矩形一模一样**（`(743,13)-(2535,979)`、`WS_CHILD|VISIBLE`、`IsWindowVisible` 为真、
`GetWindowText` 是 `keeper-calendar`），变的只有兄弟堆里那一个次序。反向也验过：摆上去→摆下来→摆上去，
两轮读数跟着走。

**同一扇窗抬成顶层窗（`WS_POPUP`）也整张画得出来** —— 所以这不是「引擎画不出来」，是**那一格排在哪里**。
（`PrintWindow` 在这扇窗上读到的是一片白：引擎不处理 `WM_PRINT`，那一发不算数，别拿它判断画没画。）

**2026-10-08 早上栽的就是这一格**：产品里发了一发 `SetWindowPos(HWND_BOTTOM)`，读它的返回值读出来
「塞到兄弟堆最底下=True」，**而屏上日历整个不见了**。`SetWindowPos` 答「发出去了没有」，
不答「排成什么样了」—— 所以产品现在自己读一次 z 序再打进日志（`DesktopLayer.RankAgainst`）。

**2026-10-12 所有者定夺：图标任何情况下都要透过来，不许被日历压住。**
契约那句「桌面图标也在它上面、也点得到」**不是取舍，是两条都要** —— 而上面那张表里
「留在图标层之上」那一档之所以压得到图标，是因为**日历那扇窗当时铺满整块工作区**。
2026-10-12 起布局减掉了左边那一条图标列（宽度由 `DesktopLayer.IconColumnWidth` 量，
读 `LVM_GETITEMSPACING`，不带指针、跨进程安全）：日历摆在它右边，那一条里什么都不画，
图标和壁纸从那里透过来。**留在图标层之上不变**，两档实测结果（画得出来 / 看不见）也仍然成立。
那一列的宽读不到时退到 110 像素，**不退成 0** —— 退成 0 等于又铺到图标上面去。
（2026-10-08 这一发是在产品自己的进程外做的：改 `SetParent` / 样式 / `MoveWindow` 三发，实拍屏，
再照 `Embed` 原样走一遍但**不发** `HWND_BOTTOM`，日历回来。量的时候被两件事带偏过一次，记在这里省得下次再踩：
① **单独发 `SetWindowPos(HWND_TOP/HWND_BOTTOM)` 动不了这扇窗的 z 序**，读数看着像「发成功了但没生效」——
真正让它落到某一格的是**改样式**（`SetWindowLongPtr` 换 `WS_CHILD`/`WS_POPUP`）；
② 顺手把样式换成 `WS_POPUP` 而没带 `SWP_FRAMECHANGED`，窗会被 Windows 判成**最小化**
（矩形跑到 `(-25600,-25600)`，`IsIconic` 为真），之后所有读数全是「看不见」—— 那一轮的实测结果作废。）



## Win+D 把日历扫走：不是最小化，是「桌面被端到前面来」（量于 10-12）

**先排掉四种猜法**。按 Win+D 前后 4.2 秒，那一扇的 `GetWindowRect`、`IsWindowVisible`、
`IsIconic`、`DWMWA_CLOAKED` **四样一个字节都没变** —— 所以「看不见」不在其中任何一样里。
屏上确实没有它（实拍：只剩壁纸和 `Keeper.exe` 图标）。

**真正的原因**（`GW_HWNDNEXT` 一步步走，实拍 + 读 z 序各一发）：Show Desktop 不是最小化每一扇，
是**把桌面本身端到前面来**。走完整条 z 序（`GetTopWindow(0)` 往下）：

| 时刻 | 壁纸层那一扇在哪一格 | 日历在哪一格 |
| --- | --- | --- |
| 稳定态 | `WorkerW`（看不见）第 129 格 | 第 132 格 |
| Win+D 后 | `Progman`（**可见**）第 **88** 格 | 第 **91** 格 |

桌面压到了日历上面，整扇就没了。**这一族和「排到 `Progman` 底下日历整个消失」是同一件事。**

**方向是量出来的，不是照名字推的**：`GW_HWNDPREV(3)` = 上一扇 = **上面**，
`GW_HWNDNEXT(2)` = 下一扇 = **下面**。判据往「上」看的那一半必须用 `GwHwndPrev`。

**硬顶 z 序顶不赢**：`SetWindowPos(hwnd, DesktopTop(), …)` 每秒发一次，Explorer 每次都把
桌面抢回上面，日志里「收之后 WorkerW/Progman 还在上面」每秒刷一次，一直刷不停。
跨进程改不了桌面那一叠的 z 序。

**能赢的是换 owner**（社区里「让窗口逃脱 Win+D」的通用写法）：
`SetWindowLongPtrW(hwnd, GWL_HWNDPARENT, FindShellDefViewWnd())` —— 把 owner 换成图标层那一扇
`SHELLDLL_DefView`。owner 不是父子关系（那是 `SetParent`），所以 `WS_EX_LAYERED` 还在，
半透没坏。**owner 认了之后 Win+D 之后日历留在屏上**（实拍 `regress-wind.png`：月、星期、
农历、格子全在，壁纸和 `Keeper.exe` 图标从底下透过来）。

**踩到的两个坑**：

1. **必须走 `SetWindowLongPtrW`，不能走 `SetWindowLongW`**。owner 是一位**句柄**，
   而 `SetWindowLongW` 第三个位是 32 位 `LONG`，写进去之后读回来还是 `0x0`。
   而 `SetWindowLongW` 返回「换之前的值」，原来没人认领就是 0 —— 拿 0 当失败判据答不出真假，
   于是日志打「owner=0x0（换成功=**True**）」，那个 `True` 是假的。
   **判据只能读回来对一遍**（`SetWindowLongPtr` 返回 owner 是不是真的换上了）。
2. **owner 只管「不被 Win+D 扫走」，不管「待在 app 窗之下」**。有了 owner 它照样是顶层窗，
   z 序仍然归调用方管。拿「有 owner」短路掉 `KeepAtBottom` 那一路，**日历就压在别的应用窗上面了**
   （实拍：盖住记事本 / VS Code / Chrome）—— 那比「Win+D 之后看不见」更严重。
   **两件事必须分开做**，见下面那一族。

**最后一族（2026-10-12 落定）**：owner 管「不被 Win+D 扫走」（shell 保证有 owner 的窗跟着
owner 走），`KeepAtBottom` 每秒管「待在所有 app 窗之下」（把它按回 `DesktopTop()` 上面）。
两条同时验才算数：`regress-notepad.png`（记事本盖住日历，日历不压任何人）
和 `regress-wind.png`（Win+D 之后日历还在）。

## 穿透能不能跨到别的进程（2026-10-11）

**问句**：铺满那一扇压在**另一个进程**的一扇窗上面时，底下那一扇收不收得到真的左键。

**为什么非要量**：所有者报「休息阶段鼠标还是无法点击到遮罩下的东西」。而当时在册的判据
（`FadeRun.Passthrough`、`Probe` 的 passthrough 矩阵）**全绿**。

**这一族的量具坏在哪（两条，读数上完全看不出来）**：

1. **口径**：判据用 `WindowFromPoint` 回谁。它从**进程内**问时会跳过答 `HTTRANSPARENT`
   的那一扇 —— 于是「这一扇不拥有那一点」读成「穿透了」。**命中测试不是点击到不到。**
2. **接收方的位置**：`ClickTarget` 那个接收方在测量程序**自己这个进程**里。
   而 `HTTRANSPARENT` 在同一线程里是真的能落下去的 —— 所以它量的是同线程那一头。

**还有一个坑：进程外问 `WindowFromPoint` 也不可信**。跨进程那一次拿不到 `WM_NCHITTEST`
的答复（`SendMessage` 的消息不到别人的 `WndProc`），于是只会回 z 序最上面那一扇。
2026-10-11 第一版量具就是这么把整块屏读成「全归遮罩」的，而同一时刻程序自己读到的是 Chrome。
**两把尺子在读数上长得一模一样。**

### 布置

两个进程，各一个：

```
# 接收方（另一个进程，纯 Win32 的 BUTTON，子类化 WndProc 数 WM_LBUTTONDOWN，
#   **普通顶层窗**——顶到 TOPMOST 会让它在遮罩落定让位之后跑到遮罩上面，
#   那一下「点得到」是 z 序给的，不是穿透给的）
Godot_v4.7.2-stable_mono_win64_console.exe --path . res://src/Probe.tscn -- --passthrough-target --selfclick --plain

# 遮罩（第二个进程，真的那一扇 Fader）
Godot_v4.7.2-stable_mono_win64_console.exe --path . res://src/FadeRun.tscn -- --hold 60 --style none
```

接收方每 1.6 秒自己点自己一下，注入走 `Win32.PressAt` / `ReleaseAt` + 让帧
（`SendInput` 三发塞进同一批那条教训），点完读自己的计数 —— **这一读数完全在接收方进程里**，
外面变的是「有没有第二扇窗压在上面」。

**每一发都印「点上那一瞬是谁」**：`WindowFromPoint` 从接收方进程问，跨进程那一次答的是
z 序最上面那一扇 —— 所以它答「遮罩」= 遮罩确实盖住那一点。**量具自己被压住时那一发不算数**
（第一版就是栽在这儿：点上那一扇是接收方自己进程的主窗）。

### 档位对照（`FadeRun --style`，候选那几位手动加到铺满那一扇上）

| 档位 | 扩展样式读回来 | `WM_NCHITTEST` | 遮罩盖住时点到 |
| --- | --- | --- | --- |
| `none`（现状） | `8000018` `\|TOPMOST` | -1 | **25 发 1 发**（盖住期间全 0） |
| `transparent` | `8000038` `\|TOPMOST\|TRANSPARENT` | -1 | **24 发 0 发** |
| `layered` | `8080018` `\|TOPMOST\|LAYERED` | -1 | **24 发 0 发** |
| `both` | `8080038` `\|TOPMOST\|TRANSPARENT\|LAYERED` | -1 | —— |

`both` 那一档**读不到「遮罩盖住时点到」** —— 因为它生效之后 `WindowFromPoint`（跨进程那个口径）
**不再把遮罩算成赢家**，那一扇整个退出命中测试。而点击是 **1/1**。
**这一档不能用同一个过滤器看**：问「点上是谁」的那一栏本来就是它答不出来的那个。

### 结论

**`WM_NCHITTEST` 的 `HTTRANSPARENT` 只跨同一个线程。** 引擎那条 `Window.MousePassthrough`
走的正是它，所以它跨不到别的程序 —— 遮罩答「这一点不是我的」是对的，底下**别的进程**
什么也没拿到，那一下就没了。

**`WS_EX_LAYERED | WS_EX_TRANSPARENT` 跨得过去**，而加上之后逐像素透明不受影响
（那两位不影响合成，采样逐通道差 0）。ADR-0003「穿透走……」那一节和设计文档 `docs/design/fader-window.md` 那两条当天跟着改。

**读数（那一发最后一次跑，2026-10-10）**：

> 顶窗 交=True 扩展写进去=8000100 读回来=8000108 NOACTIVATE=|TOPMOST|WINDOWEDGE
> 接收方=0x1B08F4 (0,0)-(420,260) 按的点=(210,130) 那个点上是谁='Button' 那个点是接收方自己=True 子类化装上了=True
> **放行（对照，一定该通）**：钩子返回=CallNextHookEx，点了 3 下，接收方 0 → 2，钩子自己看见了 3 下
> **返回非零（待证：吃掉）**：钩子返回=1，点了 3 下，接收方 2 → 2（该不动），钩子自己看见了 3 下
> 拆掉钩子之后的对照：接收方 2 → 3（该动 —— 不成立的话第二档那个「没动」就不是钩子干的）

**结论：钩子回调返回非零，那一下被吃掉了。** 三档各自证自己那一件：

- 放行档 0 → 2：**对照成立** —— 「第二档没动」不是「压根没发出去」。
- 返回非零档 2 → 2，而钩子自己看见 3 下：**事件发了、被钩子看见了、被钩子丢掉了**。
- 拆钩子之后 2 → 3：**接收方自己没坏**，它一直在收。

**放行档是 2 而不是 3 —— 这一条要认下来**：三下里有一下没进 `WndProc`。
读数上分不出是「`SendInput` 没发全」还是「发了没进」（`BUTTON` 那一扇收消息要过
命中测试，而那一发顶窗那一档和命中那一档不是同一件事，见上表最后两行）。
**它不动结论**：关键是第二档「0 下进去、0 下出来」而拆掉钩子立刻又动，
那一对的差就是钩子干的。**对照档只管「一定有反应」，不管「反应了几次」。**

**这一族的量具（`src/ClickTarget.cs`）**：一扇纯 Win32 的 `BUTTON` 顶层窗，
子类化自己的 `WndProc` 数 `WM_LBUTTONDOWN`。**为什么不用 Godot 的控件**：它要量的
恰恰是「送到了没有」，而量具不能自己要焦点（上面「Godot 的 GUI 输入」那一行）。
子类化在窗口消息进 Godot 之前，所以既不看焦点、也不看 `unfocusable`。
**它在测量程序自己这个进程里** —— 两端指的是「钩子那一侧」和「系统路由的落点那一侧」，
不是两个进程；钩子挂在全机输入的同步路径上（`dwThreadId = 0`），对自己进程里那一扇也一样有那一刀。

**产品那一族最后用的是这一条**（2026-10-10 所有者定夺「永远都不能抢鼠标，这是 bug」，
取向在 ADR-0003「点得到的那几块交给钩子按坐标判」那一节）：
**那一扇点击窗拆掉了** —— 铺满那扇一辈子穿透，「点得到的那几块」是一块矩形，

| 它的上一层链 | `SHELLDLL_DefView/0x100FC` ← `Progman/0x100F8` ← `#32769/0x1000C` |

两边条数不一样是 UIA 的视图过滤掉了非内容节点，不是读失败 —— 关键那一条是**都不为零**。
所以「UIA 跨进程枚举子节点」这一族是通的。

**于是剩下的读数就是一句：通的那些路，答出来的是 0 个条目。**
Progman 那棵树上确实一个图标节点都没有，而图标是开着的、桌面上确实有 7 个文件。

**这一份不能替它多下的一句结论**（分不清就别写）：

- **下不了**「这一版 Windows 的桌面根本不通过 UI Automation 暴露图标」。
- **下不了**「只有同完整性的调用方才看得到桌面图标」。

这两句要用同一发在**中完整性**那一侧重测才能分开。工单 07 的读法选型因此**仍然悬着**，
只是「UIA 是候选」这个猜法在低完整性下被读数否掉了，不再是首选。

**MSAA（`AccessibleObjectFromWindow`）这一族没有单独量** —— UIA 的窗口那一档
是架在 MSAA 桥上的，它通不通不是一份独立证据，所以没拿它当第二条结论。

### 这堵墙不是这台机器的规矩，是那个 exe 带进来的（量于 10-12，第三发之后）

上面那几段全都建立在一个前提上：**量具跑在低完整性**。
2026-10-12 晚一点上把那一句拆开量，发现前提本身是错的 —— 低完整性是
**`DebugProbe.exe` 这个 apphost 带进来的，不是这台机器的规矩**。

| 启动方式 | 同一个 dll，同一个父进程 | 读到的完整性 |
| --- | --- | --- |
| `DebugProbe.exe`（apphost） | 是 | **低（RID 0x1000）** |
| `dotnet exec DebugProbe.dll` | 是 | **中（RID 0x2000）** |

**怎么分出来的**（三步都是读数，不是推理）：

1. `whoami /groups` 答「Medium Mandatory Level」—— 但 PowerShell 里 `whoami` 是
   `Microsoft.PowerShell.Core\Whoami` 的别名，**报的是 pwsh 自己那个进程**，不是子进程。
   只看这一句会得出「子进程也是中」的错误结论。
2. 用 `Start-Process` 起真正的 `System32\whoami.exe`（重定向输出，拿到的是它自己那份），
   答 `Medium Mandatory Level S-1-16-8192`。所以 pwsh 是中，pwsh 的子进程也是中。
3. 同一个 pwsh、同一时刻、同一个 `DebugProbe.dll`：apphost 答低，`dotnet exec` 答中。

**产品那一侧是中的**（`产品 pid 35888 中（RID 0x2000）`，那一栏是新加的实测读数）。

**换成中之后，三个面全开**（同一发量出来的前后对照）：

| 面 | 低完整性（apphost） | 中完整性（`dotnet exec`） |
| --- | --- | --- |
| 命名管道 | `UnauthorizedAccessException` 错误码 5 | **接上了，四个动词全答** |
| `LVM_GETITEMCOUNT` | 错误码 5 | **答 15** |
| UI Automation 图标条目 | 0 个 | **15 个，带名字和矩形** |
| 往 explorer 地址空间里写 | `OpenProcess` 错误码 5 | **写进去 4 个字节** |

**所以「测量程序能不能量」这一问问错了对象。** 该问的不是「这台机器允不允许」，
是「这个 exe 是从哪条路起的」—— 同一个程序换一条起法，读数就整个反过来。

**这一条也把 07 的选型定下来了**：UI Automation 是可用的一条
（一条问句问完一整层，句子里没有跨进程指针，也不需要 `ReadProcessMemory`），
`LVM_GETITEMCOUNT` 和跨进程内存两条也都通。三条都通的时候按工单 07 的判据选**不碰对方内存**的那一条。

**为什么 apphost 会低**：这一条**还没查到**。仓库里没有 `.manifest`，
环境里也没有和完整性/沙箱有关的环境变量（量过，见下）。
**查不到就别写成结论** —— 上面那三步只证明「是 apphost 这条路带来的」，不证明为什么。

量过但没查出东西的两面：

- `Get-ChildItem` 找 `src/tools/DebugProbe` 和仓库根底下的 `*.manifest`：**一个也没有**。
- 环境和用户变量里带 `COMPAT|INTEGRITY|SANDBOX|LOWIL|BOX|APPX|MSIX|STORE` 的：**一个也没有**。

### 三条令牌读数里，有两条不可信（量于 10-12，同一次排查里拆出来的）

完整性级别那一栏是从令牌的 SID 里数 RID。**另外两条读法不可信，都已从结论里拿掉**：

| 那一条 | 读数 | 判定 |
| --- | --- | --- |
| `TokenElevationType` | 低和中**都答 3** | **分不出级别**，不能当判据。留代码是为了留证据 |
| `NtQueryInformationProcess` 的父进程号 | 读出来是 **0**（Idle） | 结构体自校验（`UniqueProcessId` 等于本进程）过了，偏移是对的，读出来仍然是 0 —— 照实报「读不到」 |

**一条分不出差异的读数和一个读错的读数，都比没有更坏** —— 前者会把「没量到」说成「量到了」，
后者会像模像样地给出一个具体的数。两条都不进结论。

顺带一个真缺陷：`PROCESS_BASIC_INFORMATION` 那个结构体原来只摆了两个字段
（`uint Reserved` + `IntPtr Parent`），父进程号在**第 40 字节**，
按原样读出来的是 PEB 地址 —— 所以那一栏一直报「读不到父进程」。现在按真实布局摆全，
并加一条自校验：结构体里的本进程号必须等于真的本进程号，不等就是布局错了。

### 输入那一族的判据自己一直是坏的（量于 10-12，同一轮拆出来的）

**2026-10-13 补一句**：`GLOSSARY.md` 的 `_Avoid_` 里列着「探针」，

`Input.ProbeKey` → `Input.F12Key`、`Input.ProbeKeyLegacy` → `Input.F11Key`、

### 为了量这一发改的那个 TFM，以及它的代价

UI Automation 在 `UIAutomationClient.dll` 里，属于 `Microsoft.WindowsDesktop.App` 这个**共用框架** ——
系统自带的一份程序集，不是 NuGet 包，所以「不引任何包」那条没被破。

代价两条，都要记住：

1. `DebugProbe.csproj` 从 `net8.0` 改成 `net8.0-windows` 并加了 `<UseWPF>true</UseWPF>`。
   **exe 起来要机器上装着 `Microsoft.WindowsDesktop.App`**（这台有 `8.0.31`）。
2. 输出目录从 `bin/Debug/net8.0/` 变成 `bin/Debug/net8.0-windows/`。

**这条 TFM 是不是为了量一次而付的永久代价，所有者定** ——
如果最后认定 UIA 这条路不通（见上面「下不了」那两句），这个 TFM 要不要退回 `net8.0`，一并定。

### 「那一点上有没有一个图标」那一问恒为真（量于 10-12，工单 09 第三发撞出来的）

| --- | --- | --- | --- | --- |

| (46,194) | 在（Comfy Desktop，第 1 颗） | **0** | 1 | 15 |

1. **消息送到了那一扇** —— 同一段代码、同一次对话里 `LVM_GETITEMCOUNT` 答得出 15。
   所以不是跨完整性、不是通道、不是超时那一支的问题，是**这一颗本身不带判别力**：

### `KeepAtBottom` 把日历从 Win+D 那一档拉不回来（量于 10-12）

产品日志每秒一行，收了又收：

```
收回：最小化=False 可见=True 收之前不在最底下：壁纸层那一扇（WorkerW）被翻到我们**上面**去了，
所以整扇看不见 → 收之后不在最底下：壁纸层那一扇（WorkerW）被翻到我们**上面**去了，所以整扇看不见
```

「收之后」那一栏和「收之前」一模一样。`DesktopLayer.cs` 的类型注释写着

所以它最迟一秒回到屏幕上」—— **这一句在这一次读数上不成立**。

**这一条不作数的地方**：z 序那一项在 08 那一发就因为「这个对话窗压着日历那一带」而不干净，
本次这一栏读的是产品自己的日志（同一把尺子、同一份读数），**没有第二把尺子对着核**。
屏幕上的实况由 09 那一发的留档帧和 `find` 那一发的命中读数兜着。

### 「抬起之后焦点端过来没有」：读数取决于抬起之前前台是谁（量于 10-12）

抬起那一段和产品自己答得出来，而抬起这个动作产品**已经带着开关**
（`Shots.cs` 的 `--lift`，直接调 `Calendar.BeginEditFromProbe`）。所以这一段单独量，
不靠双击那一段带（双击那一段被上面那个恒真的闸门挡住了）。

量法：每 50 毫秒问一次 `editmode`，**问到 `editing=1` 的那一轮立刻读 Win32 前台那一扇**。
抬起只持续几百毫秒，错过那一轮就只剩「事后」，而事后读到的前台说明不了抬起时焦点在谁那儿。

| 轮次 | 抬起之前的前台 | `editmode` | 抬起那一瞬间的 Win32 前台 |
| --- | --- | --- | --- |
| 1 | `Engine`（产品自己那一扇） | `editing=1 cell=12` | `Engine`（产品自己那一扇） |
| 2 | `Progman`（挪走那一发**没挪动**） | `editing=1 cell=13` | `Chrome_WidgetWin_1`（对话窗） |
| 3–5 | `Chrome_WidgetWin_1`（对话窗，`--away app` 明确挪走的） | `editing=1 cell=13` ×3 | `Chrome_WidgetWin_1`（对话窗）×3 |

第 1 轮那一行**不是「抬起来把焦点端过来了」**：抬起之前前台已经是产品自己那一扇，
它一直就在前面 —— 那是「什么都没换」那种相等。**单看那一轮会得出一个假绿。**

第 3–5 轮三轮一致：编辑态进去了，前台停在别的那一扇。**这一条的边界要写清**：
那一发里没有人点过产品（抬起是 `--lift` 开关做的，不是双击），
所以它拿不到「最后一次输入」那个资格，`SetForegroundWindow` 本来就可能被前台锁挡。
**它答的是「没有人点它的时候端不过来」，答不了真实双击那一条** —— 真实那一条的读数
要等闸门那个恒真的缺陷修好、双击能进去之后才量得到。

顺带量到一条：`SwitchToThisWindow` 对 `Progman` 调了**前台一格没动**（第 2 轮），
对 `Chrome_WidgetWin_1` 调了动得了（第 3–5 轮）。所以「把前台挪到别处」这一步
**必须自己再读一遍前台来判成没成**，不能拿那一发的返回值当「成了」。
### 托盘图标不在任务栏底下那一棵树里；菜单是右键出来的（量于 10-13）

### 遮罩盖满整块屏，所以「罩不住的那一块」在这台机器上不存在（量于 10-13）

`--streak 5` 让产品静 5 秒自己把遮罩抬起来，它起来的时间在 10 秒到 25 秒之间飘
（两跑分别读到「连续已经用了 10 秒」和「用了 16 秒」那一行）—— **所以量测程序要等 `swallow=1`，不猜秒数**。

起来之后量到的：

| 那一问 | 读数 |
| --- | --- |
| `swallow` | `ok swallow=1` |
| `checklist` | `ok n=3`，三行矩形 (1941,620,2307,680) / (1941,690,2307,749) / (1941,759,2307,819) |
| 屏数 | **1 块** |
| 遮罩那一扇 | `0x3C0CA2/Engine` (pid 32008)，矩形 (0,0)-(2560,1440)，**占整块屏 100%** |
| 18x10 = 180 格命中测试 | 归遮罩那一扇的 **0 格**；`Chrome_RenderWidgetHostHWND`（pid 10144）107 格、`Chrome_WidgetWin_1`（pid 31972）55 格、`Chrome_WidgetWin_1`（pid 10144）18 格 |

两条判据各自的结论，都是**缺前提**，不是「不成立」：

1. **「罩住的那一块收得到点击」答不了** —— 采样里没有一格归遮罩。
   点下去底下那扇收不到时，分不清是遮罩挡的还是别的窗压在它上面。
2. **「罩不住的那一块底下那个程序收得到」答不了** —— 遮罩那一扇自己就是整块屏，
   **这块屏上没有「罩不住的那一块」可点**。

第 0 格归遮罩这一件和产品的设计是一致的：启动日志里写着「凝实后让别的窗口盖得住」，
也就是遮罩**故意**让别的应用窗压在它上面。所以这不是缺陷，是这台机器当前的桌面状态。
**要答这两条得在这个对话窗和那个浏览器不在屏上的那一档重跑。**

顺带量到的一条判据上的坑：**接收窗收不到点击时不能直接报「被遮罩挡了」** ——
必须**点完再量一次那一格归谁**。第一次量到 0 次按下时那一格归的是 `Chrome_RenderWidgetHostHWND`，
那是 z 序，不是遮罩。两件事读数上长得一模一样，不分开就会去查错的那一件。
### 两个独立的读法在同一个数上对上了（量于 10-13，工单 07 那条判据）

工单 07 有一条判据是「鼠标是真事件 —— 判据：产品那一侧的鼠标桥读数也动了」。
产品侧那道口加了第五个动词 `mouse` 之后，这一条不用再靠量具自己的钩子单方面作证了。

三轮拖放往返（每轮按下 2 次、松开 2 次、移动 26 次）：

| | 喂 | 点击 | 丢 |
| --- | --- | --- | --- |
| 拖之前（问 `mouse`） | 0 | 0 | 36 |
| 跑完（问 `mouse`） | 0 | 0 | **48** |

量具自己的低级钩子三轮数到 **6 次按下 + 6 次松开 = 12 个事件**，
产品那一侧 `丢` 从 36 涨到 48，**正好 12**。
两个互相独立的读法（一个是量具的 `WH_MOUSE_LL`，一个是产品的桥）在同一个数上对齐，
而它们唯一的共同来源就是「这一发真的在系统输入队列里过了一遍」。

**`喂 0 发` 是闸门在正常工作，不是没喂进去**：
按下去那一点在图标上，`MouseBridge.ShouldFeed` 的第三问「那一点上有没有桌面图标」
本来就该答「有」—— 有就归 shell，图标拖放归 shell 正是要的那个形状。
**闸门把 12 发全让出去，本身也是它认出「这一点归图标」的一次读数。**
### 「三项变了，有人动过它」有可能是上一发的还原晚到（量于 10-13）

工单 03 有一条判据是「压在被测矩形上收不走的那个窗，中止前后三项读数
（句柄、可见性、矩形）完全一样」—— 理由是「要证明没碰：那是所有者的界面」。

那一发跑到一半答了相反的话：

> 第 1 轮中止：…按 IsIconic 判收走 0 扇，但 Chrome_RenderWidgetHostHWND 还压在日历矩形
> (1536,0)-(2560,1380) 上面（命中测试那一档）—— 不去动它；
> 中止前后那一扇的读数：Chrome_RenderWidgetHostHWND（pid 19468）句柄 0x206F0｜
> 发之前 可见=0 最小化=0 矩形 (0,0)-(0,0)｜现在 可见=1 最小化=0 矩形 (0,0)-(2560,1380)｜
> **三项变了，有人动过它**。

**句柄两边一样（0x206F0）**，变的是可见性和矩形：那一扇从「看不见、矩形零」变成
「看得见、铺满工作区」。**量测程序这一发一个字节都没碰它**（它只读不写），
所以那一句话会把人引到错的那一件事上。

紧接着连跑两趟，两趟都**没有**这一句，且两趟读数一模一样。合起来读：
那一次是**上一发 Win+D 的还原（`UndoMinimizeALL`）晚到了** ——
它落在这一发「发之前」和「落定之后」两次读之间，于是看起来像这一发期间有人动了它。

**这一条要记住的不是「那一扇被人动了」，是判据本身有一条盲区**：
「三项前后一样」量的是这一发期间有没有变化，而**上一发的尾巴会落进这一发的窗口里**。
连着发几发时，要在发与发之间留够时间让还原落定，或者把那一栏的读数按发编号摆出来，
别让两发的变化混成一次。

### 图标位置那一问：条数一样不等于位置没动（量于 10-13，工单 03 最后一条判据）

工单 03 判据的最后一条是「反复发 Win+D 之后，所有者的桌面图标一个不少、**位置一个没动**」。
原来那一发只读 `LVM_GETITEMCOUNT` ——**条数**，而拖走一颗再放回去条数读出来一模一样。

现在按名字配对逐颗比矩形（UI Automation 的读法，工单 07 选定的那一条），三趟各读一次：

| | 图标条数 | 逐颗比矩形 |
| --- | --- | --- |
| 第 1 趟 | 15 → 15 | 一个没少、一个没动 |
| 第 2 趟 | 15 → 15 | 一个没少、一个没动 |
| 第 3 趟 | 15 → 15 | 一个没少、一个没动 |

三趟的收走集合也一致：每一趟都只收走 `Chrome_WidgetWin_1@0x106D2` 一扇、放回来 0 扇。
落定等待 492 / 479 / 900 毫秒、采样 2 / 2 / 4 次，**都是读到两次一样才继续**。

### 「每一次动作之后读图标位置」补到剩下几发（量于 10-13 凌晨）

契约第四节要的是**每一个动作**之后都抓一帧、读归谁、读图标位置。上一条只补了清场那一发。
这一轮把剩下四发补齐：扫桌面（`sweep`，每一轮 Win+D 各读一次）、托盘菜单（`tray`，
右键点开和悬停展开各读一次）、遮罩抬落（`cover`，点之前和两下点完之后各读一次）、
双击进编辑态（`edit`，双击前后各读一次）。

**比法只有一把尺子**：`Icons.ComparePlaces` 按名字配对逐颗比矩形。
清场那一发原来有一份私有副本，口径和别处各写各的，已经删掉。
返回句**不带「图标位置：」这几个字**，标签由各发自己写 ——
标签带着「哪一轮」「点开之前」这些上下文，各发才知道怎么叫它。

五发在屏干净时（`find` 读到 25 格全归壁纸层、别家窗 0 扇）的读数：

| 那一发 | 读了几次 | 读数 |
| --- | --- | --- |
| `clean` | 2 | 15 → 15，一个没少、一个没动 |
| `sweep --rounds 3` | 6（每轮两遍） | 三轮都是 15 → 15，一个没少、一个没动 |
| `sweep --rounds 2` | 4 | 两轮都是 15 → 15，一个没少、一个没动 |
| `tray` | 3（点开前、点开后、子菜单读完） | 三次都是 15 → 15，一个没少、一个没动 |
| `cover` | 2 | 15 → 15，一个没少、一个没动 |
| `edit` | 2 | 两趟都是 15 → 15，一个没少、一个没动 |

**六发、十七次读数，一个图标都没被这些动作动过。** 读数用的那一句把图标层本身也摆了出来
（`图标层 0x100FE（pid 9004，(0,0)-(2560,1440)）……直接子节点 15 个，15 颗`），
层换了或子节点数变了都看得见 —— 不只是一句「15」。

### z 序那一问：屏干净时它作数了，读数是每次 Win+D 翻一档（量于 10-13 凌晨）

工单 08 那两条判据（z 序位置、图标命中）上一轮都记着「不作数」——
两侧总有一格归 `Chrome_RenderWidgetHostHWND`。这一轮屏干净了
（25 格全归壁纸层），**这两项成了作数项**，于是读数直接露出来：

| 那一轮 | z 序（发之前 → 发之后） | 同一个点命中 |
| --- | --- | --- |
| 第 1 轮 | 第 90 → **数不到** | `SysListView32` → `SysListView32` |
| 第 2 轮 | 数不到 → 第 90 | `SysListView32` → `SysListView32` |

**每一次 Win+D 翻一档。** 「数不到」是 `ZIndexOf` 的原话（`ZOrderTop(120)` 那一串里没有它），
不是「排在第 0 位」。

分开「是 Win+D 动的」和「它自己在动」，办法只有一个：**不发 Win+D，只连着读**。
为此给 `sweep` 加了 `--watch-z N`（每 250 毫秒读一次，共 N 次，把连续相同的分档摆出来）：

| 那一跑 | 读数 |
| --- | --- |
| `--watch-z 40`（10 秒） | 40 次全是数不到，**一档到底** |
| `--watch-z 16`（4 秒） | 16 次全是数不到，**一档到底** |

10 秒跨过产品十个「每秒收一次」的循环，一次也没换档。
**所以那一格的跳动是每次 Win+D 翻一档的后果，不是它自己在动。**

还有一格没量到：**顶上去之后多久自己落回来**。上一次 `sweep` 收尾时读到第 90，
下一格 `--watch-z` 起手就答数不到，中间没发过 Win+D —— 说明 90 会自己落回去，
但落回来要多久没量。要量它得连着读并在中途发一次 Win+D，`--watch-z` 现在还做不到这一点。

## 覆盖法那一族收不回来：读数和它的机制（量于 10-13 16:00）

用户报三个症状：图标被日历盖住、图标拖得动但没有拖动的动画、把图标往日历里拖之后桌面几乎卡死。
关掉 Keeper 之后，把被日历盖住的那个图标往外拖，**建出来的是一个快捷方式，原图标没动**。

**先看顶层那一族一次运行的日志**（`Keeper/logs/godot.log`，10-13 15:47 起，15:50 用户退出）：

```
15:47:12.852  摆上 …压在桌面 WorkerW 正上方 … 不在最底下：壁纸层那一扇（WorkerW）被翻到我们上面去了
15:47:13.649  收回：… 收之前不在最底下：…（WorkerW）被翻到我们上面去了
              → 收之后不在最底下：…（WorkerW）被翻到我们上面去了
15:47:14.670  收回：…（同上）
```

**收之前和收之后逐字相同**，每隔 1.01 秒一次，一路刷到退出。

### 机制：判据找的那一扇，正是动作插进去的那一扇

1. `DesktopTop()` 从 z 序最顶往下走，取**第一扇**壁纸层窗（`Progman` / `WorkerW` / `DefView`），拿到 `WorkerW`。
2. `SetWindowPos(日历, WorkerW, …)` 把日历插到 `WorkerW` **正上方**。
3. `Above()` 从日历**往上**找壁纸层窗，第一扇就是刚插到紧上面的那扇 `WorkerW`。
4. 判「不在最底下」→ 下一秒再插一次。

**这一族在这台机器上不可能收敛**，和 Explorer 有没有抢是无关的。

### `DesktopTop()` 为什么会挑中一扇空窗

枚举顶层窗 298 扇，壁纸层那些的读数（`visible` / 子窗）：

```
0x406F0 WorkerW visible=False children=(none)
0x20212 WorkerW visible=False children=(none)
…（共 12 扇，全是「不可见 + 无子窗」）
0x100F2 Progman visible=True children=SHELLDLL_DefView[SysListView32,SysHeader32]  SysListView32[SysHeader32]  SysHeader32[]
```

**12 扇 `WorkerW` 全是空的、不可见的**。而 `DesktopTop()` 不筛可见性，所以它挑中的是某一扇占位窗，
日历插到它之上 —— 而那一扇在 z 序里的位置和图标层没有关系。

**本机的形状是 Win11 24H2+ 那一版**：`Progman` 底下直挂 `SHELLDLL_DefView`，`SysListView32` 在它里面，
**没有承载壁纸的 `WorkerW`**。所以「挂在壁纸之上、图标之下」那一格现在根本不存在。

### 图标层和日历不在同一棵树上

`GW_HWNDPREV` 从日历往上走到顶，**一步都没撞见图标层**（读数 −1）。图标层是 `DefView` 的子窗，
而日历是顶层窗 —— 两条 z 序链根本不相交。所以 `Above()` 永远只能在顶层那几扇壁纸窗里挑。

### `SetParent` 改父子关系跨进程不成立

`DebugProbe embed` 那一发（独立进程，纯 Win32）从外面发 `SetParent` + 改样式，挂之前挂之后读数：

```
[挂前] 爹=0x100F6/SHELLDLL_DefView 样式=|POPUP  矩形=(1536,0)-(2560,1380)
[挂后] 爹=0x100F6/SHELLDLL_DefView 样式=|POPUP  矩形=(1536,0)-(2560,1380)
```

**父和样式一个字节都没变。** 父子关系要同一线程，跨进程发不出去。

**后果**：「挂进桌面层」这一发**只能由产品自己发**，搬不进独立量具。
挂载那一族要对比着量，只能靠同一个二进制切着跑（现在那个开关是 `KEEPER_PARK=embed`）。

### 挂进 `DefView` 排在图标层之下：跑通了，但日历整扇看不见

产品自己发那一发之后的读数：

```
挂进 DefView：爹=0x100F6/SHELLDLL_DefView（SetParent 答 0x1000C）
样式=|CHILD|VISIBLE  扩展样式=|TRANSPARENT|LAYERED
矩形=(1536,0)-(2560,1380) 1024x1380 和要的一样=True
图标层 0x100FA 的上一扇=0x0/none
```

**成了的三件**：

- 爹换成 `DefView`，样式变 `WS_CHILD`。
- 扩展样式补上 `WS_EX_LAYERED | WS_EX_TRANSPARENT`。
- **12 秒内 0 行「收回」** —— 那一族一秒都不抢了（同一份二进制，不带开关跑，同一段时间是每秒一行）。

**样式位的顺序是一条实测**：先 `SetParent` 再改样式，扩展样式读回 **0** —— `LAYERED` 丢了，
于是那是一扇 1024×1380 的**不透明**窗挂在图标层里。改成「先改样式、再换爹、换完再补一次」才读回
`|TRANSPARENT|LAYERED`。屏幕抓帧也印证了：第一版抓到的桌面图标一个没少（说明没被盖），
但同样看不见日历。

**「挨着图标层」那个判据两次都问反了**。`SetWindowPos(h, 图标层, …)` 是把日历插到图标层**之下**，
而图标层本来就是 `DefView` 子窗堆里最底的那一扇，所以：

- 从**日历**往下走（`GW_HWNDNEXT`）撞不到任何东西（读数 `0x0`）—— 它成了新的最底。
- 从**图标层**往上走（`GW_HWNDPREV`）也撞不到（读数 `0x0`）—— 它本来就是最上面的那一扇。

两条读数同时成立才说明位置是对的。**判据得问「图标层的上一扇是不是我们」还是「我们是不是 `DefView` 最底的那扇」，不能问「挨着没有」**（挨着的那一扇永远是 0，问不出差别）。

**没解决的那一件**：按 Win+D 清场之后抓帧，**桌面图标一个没少**（不透明的问题修掉了），
**但日历整扇看不见**。图标层是**不透明**的，铺满 `DefView` 整块客户区，把排在它底下的日历全挡住。

于是这台机器上两件不能同时成立：

| 摆法 | 日历可见 | 图标能拖 | 要抢 z 序 |
| --- | --- | --- | --- |
| 顶层 + `LAYERED` | 是 | 否（鼠标落在日历上） | 是，每秒 |
| 挂 `DefView`，图标层之下 | 否 | 是 | 否 |

### 往下走那 1 扇是谁：顶层链 300 扇的读数（量于 10-13 16:26）

从日历往下走（`GW_HWNDPREV` 的反面 = `GW_HWNDNEXT`）头几扇：

```
1. MSCTFIME UI              vis=False 0x0
2. IME                      vis=False 0x0
3. PseudoConsoleWindow      vis=True  0x0
4. CASCADIA_HOSTING_WINDOW_CLASS vis=True 1199x616
…
7. Chrome_WidgetWin_1       vis=True  2062x1118
```

## 量具自己站错了位置（量于 10-13 17:00）

量具（`DebugProbe`）读桌面图标层时，全答「读不到」。

### 读数：同一个二进制，只换目录

| 放在哪 | 它的 RID |
| --- | --- |
| `%TEMP%\keeper-debugprobe` | `0x2000`（中） |
| `src\tools\DebugProbe\bin\Debug\net8.0-windows` | `0x1000`（低） |

### 根因：仓库目录上两条显式的 ACE

`Get-Acl` 读数：

### 量具现在怎样

1. **完整性低于 explorer 就换一个地方重跑自己**（`Relaunch.cs`）。
2. **换完还是低就当场拒收**，并把该跑的那条命令原样交出来。

第 2 条和 `.scratch/debug-tool/SPEC.md` 第三节第 2 条同一规矩 ——「读到别家窗，当场拒收」。

（`UnauthorizedAccessException`）。所以复制那一发必须由中完整性那一侧的 shell 做。
`src\tools\DebugProbe\run.cmd` 就是它 —— 从 PowerShell 里跑它，跑出来就是中完整性。

### 拒收那一发交出来的命令，自己也错过一次（量于 10-13 17:57）

**拒收这个动作是对的，交出去的那条命令是错的。**

实测：直接从仓库 `bin` 里跑那个 exe，它拒收了（`RID 0x1000` vs explorer `0x2000`）。
但它交出来的第一条 copy 是 `.dll`，最后一行去跑的是 `DebugProbe.dll`。

**根因**：exe 名是从 `GetEntryAssembly().Location` 取的 —— 那一处指的是**托管程序集**
（`DebugProbe.dll`），不是 apphost 那个 exe。.NET 的 apphost 按 `<程序集名>.exe` 命名，
**从程序集名推才对得上**。

**同一个错在换地方重跑那一发里也有**：它复制的是 `dll`、`dll`、`runtimeconfig.json`，
`.exe` 根本没复制，然后拿那个 dll 去起。
那一发从来没走到过（低完整性进程写不进 `%TEMP%`，先崩在复制上），所以这个错一直没露。

**第二个错**：交出来的命令**不建目标目录**，而 `copy` 不会建目录。
照抄那几行，第一条就报「系统找不到指定的路径」。
而且 `copy /y` 是 cmd 的写法 —— PowerShell 的 `copy` 别名不认 `/y`。
所以那一段要说死「拿一个中完整性的 **cmd** 跑」，不能只说「shell」。

改完再验一遍：从拒收输出里把那几行**抠出来原样喂给 cmd**，
5 行全过（3 个文件复制成功），量具从 `%TEMP%` 起起来，`selftest` 答完，
从那儿跑 `icons` 读回 `RID 0x2000`。

## `cmd` 里的中文：实测两种写法都不成立（量于 10-13 17:45）

`run.cmd` 第一版是中文注释 + UTF-8 无 BOM。跑出来是一堆
`'性进程读不了' 不是内部或外部命令`。

**机制**：`cmd.exe` 按 **OEM 代码页**（这台机器是 936/GBK）读 `.cmd`。
UTF-8 的字节按 GBK 重新解码，某些字节对解出来带 `0x5C`，
`cmd.exe` 把它当**行接续符** —— `rem ...` 那一行于是被拆成命令。

试过 `chcp 65001`，**不管用**：换完代码页之后 `cmd.exe` 按**字符数**回退文件偏移，
落进行中间。

| 写法 | 结果 |
| --- | --- |
| UTF-8 中文，不改代码页 | 失败：`'...' 不是内部或外部命令` |
| UTF-8 中文 + `chcp 65001` | 失败：同样的错 |
| 纯 ASCII | 通过 |

所以 `run.cmd` **只写 ASCII**。中文的「为什么」留在 `Relaunch.cs`（C# 按 UTF-8 读，可靠）
和本文这一节 —— 一条事实只活在一处，`.cmd` 里不抄第二遍。

## `DefaultOutDir()` 边找边建，造出 7 个空的 `.scratch`（量于 10-13 17:52）

### 一帧里花多久（这一问是每帧走的）

鼠标桥第三问由 `Calendar._Process` 每帧调 `MouseBridge.Drain` 带进来，所以要分清两件：

| 那一问 | 用时 | 量法 |
| --- | --- | --- |
| **读一次**（跨进程 COM，`DesktopIcons.ReadNow`） | 同一发里连读三遍：空闲时 **165 / 67 / 69 毫秒**，机器忙时（刚导过一次产物）**181 / 130 / 136 毫秒** | `--icon-columns` 同一发里同步读三遍 |
| **帧里那一问**（`DesktopIcons.OnIcon`，5 颗图标，比矩形） | 单次 **0.026 / 0.028 微秒** | 同一发里问 20000 遍除一下 |

**所以读不在帧里做。** 一帧 8 毫秒，读一次就吃掉两帧以上；连每秒一次也是每秒一次
几十毫秒的跨进程 COM。实现是：读在后台线程上（`DesktopIcons.RequestRefresh`），
两次读之间隔 `RefreshMs`（2000 毫秒），帧里只拿上一次那份快照比矩形。
一帧的代价是那 0.03 微秒 —— 相对那一帧 8 毫秒量不出来。

**踩到的那一下（JIT，不是运行期）**：第一次跑时抛 `FileNotFoundException: UIAutomationClient`，
而 `try` 根本没进去 —— 编译器把 UI Automation 的类型记进 `ReadNow` 这一个方法，
JIT 在**进方法门那一刻**就要把那些类型解析出来，而程序集还没装。
装程序集那一发必须与提 UIA 类型的那些方法**分开两个方法**，见 `src/DesktopIcons.cs`
`ReadNow` / `ReadByUia`。取向与代价记在 ADR-0003 那一节。

### 量产品那一发的 CPU：`Godot_v4.7.2-stable_mono_win64_console.exe` 是壳，采到它读不出产品（量于 10-14）

**这一条不是读法的事**，是量产品那一发进程的办法。记在这里是因为它和上面那一节量的
是同一个产品进程，而且结论是「没问题」，得有个地方把「原来以为冻住了」这件事钉住。

**症状**（工单 26 落地后复核报的那一发）：起产品之后逐 5 秒采一次进程，
读数是 `CPU=0.02 线程=4 WS=6MB`，最后掉到 `线程=1`；日志停在 14 行，
最后一行是 `前台应用=…`，之后再没有 `port` 那一行和「桥：喂=…」那一行。
逐层 `git stash` 排除之后指向「TFM 切换 + `src/DesktopIcons.cs` 那一族」。

**根因**：那颗 `_console.exe` **不是产品进程，它是个壳**。它自己起一个
`Godot_v4.7.2-stable_mono_win64.exe` 当子进程，然后等着。采壳的 pid，采到的就是壳：

| 进程 | 角色 | CPU | 线程 | 工作集 |
| --- | --- | --- | --- | --- |
| `…_mono_win64_console.exe` pid 17116 | 壳，等子进程 | 恒 0.00 | 恒 4 | 恒 6MB |
| `…_mono_win64.exe` pid 24824 | 产品（父 = 17116） | 1.44 → 2.27 → 2.97 → 3.56（每 5 秒） | 恒 43 | 241..250MB |

**主循环好好地在跑**，三样各自答得出来（同一发，带 `--probe-port --calendar`）：

- `port` 那一行：「口开着：Pump 平均 **3.3** 微秒（**598** 帧）」——
  5 秒 598 帧，约 120 帧/秒。
- 「桥：喂=0 点击=0 丢=0 …」每 5 秒一条，图标列答「图标 5 颗，让开 1 段 (2046)-(2138)」。
- 换**不带壳**那一支 exe（`Godot_v4.7.2-stable_mono_win64.exe`）起同一个场景，
  单进程，无歧义：CPU **1.69 → 2.50 → 2.92 → 3.58**，线程 **43**，工作集 241..251MB。

**「日志停在 14 行」也是对的，不是症状**：不带 `--probe-port` 就不建那道口，
所以不会有 `port` 那一行；不带 `--calendar` 就没有每 5 秒那一条「桥：喂=…」。
`foreground` 那一族只在换人的那一刻印一行，前台没换就不印。同一个旗子组合下，
一次**正常**的运行就是 14 行、最后一行是 `前台应用=…` —— 与报上来的症状逐字相同。

**反向验（这一条是判据）**：拿同一颗 `_console.exe` 起一发**一定活着**的场景
（`--headless --quit … Probe.tscn -- --check`），只采壳的 pid：

```
第 2 秒  壳 CPU=0.00 线程=4 WS=6MB     真身 pid=17304 CPU=4.50 线程=34 WS=422MB
第 6 秒  壳 CPU=0.00 线程=4 WS=6MB     真身 pid=17304 CPU=8.95 线程=35 WS=584MB
第10秒  已退，壳退出码=0，56 组 0 条问题
```

**「CPU 冻在 0、线程 4、工作集 6MB」这一组读数，在一次确定健康的运行上照样出现。**
所以它量的是壳，不是产品。

**为什么 HEAD 那一版读起来「正常」**：对照用的是打包产物 `Keeper.exe`，
那是**单进程**，采到的就是产品本身。这两条路量的不是同一个东西 ——
**换测量对象之后拿两边的数对比，量的就不是同一件事。**

**采的时候怎么办**：

1. 要产品那一发的数，就采子进程（`Get-CimInstance Win32_Process` 的 `ParentProcessId`
   指着壳那一个），或者直接起不带壳那一支 exe。
2. 要一道**一定该停**的判据退出码，就用 `_console.exe` —— 壳把子进程的退出码原样带出来
   （上面那次 `--check` 读到 `0`）。

## 静止时不重画：引擎那一档（视口更新档位）管不住这一扇（量于 10-14）

**问的那件事**：桌面日历摆着的时候，内容一个月不变一次，而它是一扇每像素透明的顶层窗
（`WS_EX_LAYERED`，`DesktopLayer.Park`）——能不能让引擎**别每帧重画这一块**。

**答案（2026-10-14 本机）：不能。**引擎确实有这一档
（`RenderingServer.viewport_set_update_mode`，三档 `Disabled` / `Once` / `WhenVisible`），
设下去读回来也是我们设的那一档，而这一扇的帧照样每帧重画，CPU 读数与改前不可分辨。

### 量法

三发并排，同一颗引擎（`4.7.2-stable_mono_win64_console.exe`）、同一份工程，
**只换 `Keeper.dll`**（改动那一版编出来的 `Keeper.after.dll` 与 HEAD 那一版编出来的
`Keeper.before.dll` 轮流拷回去），旗子一样：

```
<引擎>_console.exe --path . res://src/App.tscn -- --calendar --probe-port --anyway --data <临时目录> --seconds 42
```

每一发**起跑十秒之后**再量二十秒，取那个进程自己的 CPU（`Get-Process` 的
`TotalProcessorTime` 差）。帧率读数取 `--probe-port` 那一行（`ProbePort.ReportCost`）。
像素读数走另一发：`--calendar --shot --sweep`，三点（同一点读两次：窗开着、
`SW_HIDE` 之后；差就是屏幕上有没有我们的像素，`Shots.AlphaMeasurement`）：

```
<引擎>_console.exe --path . res://src/App.tscn -- --calendar --anyway --sweep --data <临时目录> --shot <png> --seconds 40
```

改前那一发不并排跑：先量改后那一版，再把二进制换回去、改回去、再量一次 —— 机器上别的
负载（终端、浏览器、用户自己那一发打包版）一直在动，并排跑的那两发之间差一两个百分点
是常事。

- **量到了**：这一档按成 `Disabled` 之后，这一扇窗的帧照样每帧重画（反向验那三行读数），
  CPU 与改前不可分辨（上面四行）。

  `RenderingServer.ViewportGetRenderInfo` 的第三个参数在 C# 绑定里是**按值**传的（返回 `int`），
  读不回值。
- **量不到**：引擎到底有没有把档位按回默认。读回 `Disabled` 的那个位置（`_Process` 开头）
  是被**我们自己上一帧的设置**填的，所以那一行是自我实现的读数，证明不了引擎的态度。
  能分开这两件事的那个位置（画之前、引擎按完之后）在 C# 侧不存在：
  **`Window` 收不到 `NOTIFICATION_DRAW`**（`CanvasItem.NotificationDraw`）——
  那一发一秒里来了 **0 回**，而且这颗引擎的 C# 绑定里也没有 `Window._Draw` 这个虚方法
  （实测：报「没有找到适合的方法来重写」）。
- **量到了（顺带）**：同一颗引擎、同一份二进制在不同时段量出来的 CPU 能差一倍以上
  （同一天上午那三发「日历关着」读到 11.3% / 11.9% / 11.8%，下午这两发读到 6.7% / 7.3%）。
  所以「三发并排只换设置」那种量法在这台机器上必须配**并排重跑**，一次一发的读数不作数。
- **量到了（同一天下午，并排重跑两轮）**：上面那组时段噪声不影响**并排**读数 ——
  两发同时起、同一段窗口里各量自己那个进程，两轮都复现：

  | 那一轮 | 日历开 | 日历关 |
  | --- | --- | --- |
  | 第一轮，20 秒 | 10.4%（pid 27184） | 4.8%（pid 25896） |
  | 第二轮，30 秒 | 11.8%（pid 27184） | 5.2%（pid 25896） |

  同一台机器、同一个时刻、两发只差 `calendar.enabled` 这一条，
  **开着日历那一发是关着的那一发的两倍多**，两轮都在两倍附近。
  身份是各自口开上那一行印出来的（`keeper-probe-ZQH12-27184` /
  `keeper-probe-ZQH12-25896`），配「开的那发日志里有 `摆上`、关的那发没有」，
  不靠进程号大小猜。

  **所以「日历那一扇每帧重画」这件事本身是站得住的** ——
  站不住的是上面那一版改动（视口更新档位拧不动它，见反向验）。

#### WorkerW 那条路：画布确实在，之前是找法错了（量于 2026-10-15 13:45）

### 量法上撞到的一处：窗口过程返回 0 会让 `CreateWindowEx` 当场失败，错误码还是 0

量具那一族的窗类窗口过程是 `DefWindowProc`（`src/tools/DebugProbe/Layered.cs` 的 `Keep` 那一族）。
产品那一族原写的是 `(_, _, _, _) => IntPtr.Zero` —— **建窗当场就失败了**：
`WM_NCCREATE`（`0x0001`）答 0 等于答 FALSE，`CreateWindowEx` 立刻返回空句柄，
**而 `GetLastError` 读出来还是 0**。两边的 `WindowClassEx` 结构体逐项相同
（同样字段次序、同样 `Marshal.SizeOf`），所以 `cbSize` 和 `RegisterClassEx` 都没问题 ——
**差别只在窗口过程**。

所以：**失败文案不能写死「窗类注册失败」**。`RegisterClassEx` 和 `CreateWindowEx` 是两个失败点，
错误码各自读、各自报，否则下一发坏的时候那句话指不到是哪一步。
真机那一跑的日志就是被这一句带偏的（2026-10-15，应用日志两行：
`建不出那一扇原生窗（窗类注册失败，错误码 0）`）。

## 层叠子窗只推一次、壳重画之后不补推（机制读代码读出来，读数见上一节）

**这一节不是量出来的，是读代码读出来的**（`src/Calendar.cs` 的 `_Process` 和 `PushPixels`、
`src/NativeLayer.cs` 的 `Watch`/`ShouldReadBack`）。上一节那三档读数是它成立的事实。

### 机制：四步，每一步都能在代码里指到

1. `Calendar._Process` **每帧**都调 `PushPixels("画面变了")` —— 每帧调，不是每帧推。
2. `PushPixels` 的早退条件是 `!force && !_dirty && !sizeChanged` 就 `return`。
   `_dirty` 由 `Paint` / `ApplyLayout` 那些真的改了画面的那一发置上。
3. `Win+D` 之后，产品侧**什么也没变**：宿主还是那一扇（`DefView` 句柄没变）、日历内容一个字没改、
   `_placedAt` 那一块没变。所以 `_dirty` 从那一刻起恒假。
4. ⇒ 从 `MinimizeAll` 那一刻起，**没有任何一支会再推一次**。要等到有人翻月、选日或者过午夜 ——
   那三件都会 `Paint`，都会把 `_dirty` 置上，推出去，日历才回来。

**壳那一侧发生了什么**：`MinimizeAll` 让壳重画了桌面，而层叠子窗缓存的那张面归 DWM 管，
重画把那张面丢了。产品没收到任何通知（没有消息、没有事件、句柄没变），
所以它的判据（画面变没变）压根看不到这件事。

### 为什么原来那两族都答不出这一档

| 那一族 | 它问什么 | 这一档的答案 |
| --- | --- | --- |
| `ShouldReadBack`（画面变了才读回） | 引擎这一侧的画面变没变 | **恒假** —— 内容一个字没改 |
| `HostChanged`（看门狗） | 宿主换了没有、那一扇还在不在、可见不可见 | **四样全对** —— 它答不出「那张面没了」 |
| `KeepEngineWindowHidden` | 引擎那一扇是不是被谁显示出来了 | 不相干 —— 它压根不看像素 |

**读回是同步的**（一帧里要把 5,652,480 字节读回来再逐像素转 BGRA，1,413,120 次），
所以改成「每帧读回来重推」是直接否掉的。补推只能**按周期**做。

**顺带记一条（给下一个来的人）**：表里前两问**现在只有自检在拧** —— `ShouldReadBack`、
`HostChanged`、`ShouldReattach` 全仓没有生产调用方（`PushPixels` 自己按 `_dirty` 和尺寸判，
看门狗那一发自己按 `Watch()` 的返回值判）。这一族里**唯一被产品真的调用的是 `ShouldRepush`**
（`Calendar.Tick` 那一段）。**自检绿不等于产品照着判据走** —— 接线那一层自检看不见。

### 修：看门狗那一轮之外，到点补推一次

`NativeLayer.ShouldRepush(attached, sincePush, periodSeconds)` + `RepushSeconds = 5`，
`Calendar.Tick` 里那一段（和看门狗并排，问的是另一件事：看门狗答「要不要重挂」，
这一发答「要不要补推」）。

**判据里没有宿主那一位，是有意的**：它钉的就是「宿主没变、到点也推」。
不到点不推那一头由 `sincePush < periodSeconds` 那一格钉住 —— 不到点就推等于回到每帧读回。

**周期为什么是 5 秒**：下限是 1 秒 —— 那就是每帧读回；上限是看门狗那个 30 秒 ——
空白会停满 30 秒，而这一块是 1024x1380，停几秒就看得见。5 秒是这两头之间最粗的一档。
**真机那一发要量的就是「空白最多停多久」**。

**补推成功不记日志**（一天一万七千多行会把应用日志淹掉），答假那一行无论什么时候都记。

### 反向验（`--check`，全程 `dotnet build -t:Rebuild`）

## 量具认日历窗的判据过期：改成认那一扇原生子窗（量于 2026-10-15 晚）

量具（`src/tools/DebugProbe/`）的 `Find.CalendarWindow()` 原来按
「产品进程 + 类名 `Engine` + 爹是壁纸层那三类之一 + 顶层窗」找日历那一扇。
产品那一侧已经换成自己造的原生层叠子窗，那一族的判据整条作废了。
`shot` / `find` / `cover` / `refuse` 都经过那个方法，于是四发一起拒收。

### 新判据读到的那一扇

量的是当时在跑的那一份：桌面上的 `Keeper.exe`，pid 22536。
`run.cmd find --dump`（顶层窗那份清单之外另加了一行日历候选）：

## 推进去的 alpha 被整块当成 255：`BLENDFUNCTION` 那四个字节（量于 2026-10-17）

**症状**：日历那一块在屏上是**纯黑**，连格子之间的缝也是黑的。
量 `clean-after.png`（1682×1050），抽样里 **57% 是 `(0,0,0)`**。

**推进去的那一份是对的**。读回来 1024×1380、格式 `Rgba8`，最多的四种颜色是：

```
(0,0,0,94)×766352   (0,0,0,112)×328743   (0,0,0,34)×146398   (0,0,0,0)×96410   颜色种数=1242
```

那三档 alpha 就是 `CellBackground`（`src/Calendar.cs`）铺在格子里的底：
`0.42 / 0.50 / 0.15` 乘 `calendar.opacityPercent` 的默认 **88** 乘 255
= **94.2 / 112.2 / 33.7** —— 三档逐一吻合。**那是半透的黑，不是黑。**

**病根**：`Update` 那一发交给 `UpdateLayeredWindow` 的 `BLENDFUNCTION` 是
`BlendOp=0, BlendFlags=0, SourceConstantAlpha=0xFF, AlphaFormat=0`。
`BlendFlags=0` 的意思是「**按 `SourceConstantAlpha` 混**」——源位图自己的 alpha 通道
根本不参与；再配上 `0xFF`，就是**整块按不透明画**。于是 `alpha=94` 被当成 255，
那层半透的黑落下来成了纯黑。

改成 `BlendFlags = AC_SRC_ALPHA(1)`、`AlphaFormat = AC_SRC_ALPHA(1)`，
`SourceConstantAlpha` 保持 `0xFF`（`BlendFlags=1` 时它不参与）。改完量到：
壁纸透上来、字压在壁上、图标画在日历上面。

**2026-10-29 复量改写**：图标不是画在日历上面，是**隔着日历的暗纱透过来**。
那一帧分不出「压在上面」和「半透着透过来」。读数与判据见本篇
「层叠子窗合成在图标上面」那一节。

**为什么量具那一族当初没发现**：`run.cmd layered` 推的是**不透明纯色**
（`new byte[] { Fill.B, Fill.G, Fill.R, 0xFF }`），blend 同样全 0。
对一颗不透明的像素，硬边和按 alpha 混**没有分别** ——
所以「19200 / 19200 个像素变」答得出「推进去了」，**答不出 alpha 有没有被认**。
