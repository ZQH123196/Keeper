# 测量程序和判据自身的坑：测量程序坏的时候报的还是一个合法实测结果

这一族是 `Probe.cs` / `FadeRun.cs` 这些测量程序自己的形状问题，不是产品行为问题。同一件事的取证规矩在 `CODING_STANDARDS.md`，这一份只记测量程序咬过人的具体场合。
这一族的共同形状是：**测量程序自己坏的时候，它报的还是一个合法的实测结果。**

- **`--check` 的实测结果只在 `dotnet build` 成功之后才算数**：build 失败那一回它照样报一组「0 条问题」，
  那是**旧 DLL** 在说话。组数别抄，这一跑自己印。
- **「改了源码却跑出旧实测结果」不一定是判据坏了，是增量 build 按时间戳判的**（2026-10-05 量到）。
  `Copy-Item` 把一个**备份**盖回源码时，文件的 mtime 回到备份那一刻 —— 早于上一次 `dotnet build`
  产出的 `.godot\mono\temp\bin\Debug\Keeper.dll`。于是 `dotnet build` 判定「没什么要重编」，
  屏幕上 0 错误 0 警告，而 `--check` 跑的是上一次那份二进制。**认法**：比 mtime ——
  `Get-Item src\X.cs` 和 `Get-Item .godot\mono\temp\bin\Debug\Keeper.dll`，源码比 dll 老就是这一种。
  绕法两条：`dotnet build --no-incremental`，或者 `Copy-Item` 之后碰一下文件（`(Get-Item f).LastWriteTime = Get-Date`）。
  **症状和「判据是空壳」一模一样**，而第一反应一定是去怀疑判据 —— 那一族已有的坑
  （上面「改完要反向验一次」那几条）都会把你引到同一个错方向。
- **别拿 `App.tscn` 跑 `--check`**：拿错场景那一发没跑一次自检，走的是「让路 → 递窗」，副作用是把桌面上那扇
  设置窗又举起来；第二发 `App.tscn` 退成 exit 0/1 是**让路不是崩**，kill / 重启之前别拿它的退出码当故障实测结果。
  自检跑的是 `res://src/Probe.tscn -- --check`。
- **无头自检的实测结果是可重复的**：同一份 build 连跑几发，归一（只去掉行首时间戳和 `pid=`）之后**逐字相同**，
  退出码也稳。所以「跑完实测结果一个字都没变」是一条**能量**的验收，不是愿望 —— 前提是归一那个尺度要窄：
  只去时间戳和 pid，别的都留着比。（量于 2026-09-29）
- **自检里有几组要一棵活节点树，不是「两个不需要窗的自检」**：`Probe.cs` 头上那句话当时是错的，已改准。
  哪些组要活树、哪些只跑纯算术或自己那个用完就删的临时目录，**以那一跑印出来的分组为准**，这里不列名单
  —— 名单会漂，而它每改一次就多一处要同步的地方。
- **`Scheduler.StepMs` 对「只有一步且 `ms:0`」那一档还回 `null`**（没有到期时间），不是
  `max(0, fadeInMs)`。「第一步把淡入算进自己的长度」只对**不是最后一步**的第一步成立。
  写断言时按 max 那条公式写，当场报「事件带的是空」—— **代码是对的，断言是错的**。（量于 2026-09-29）
- **一个每帧都成立的事件发出来，计数型的订阅方会被骗到恒真**：认「几块屏都落定了」的那种订阅方，
  一块屏落定之后帧数够多就能把计数凑满。赋一个 bool 的订阅方看不出来，所以赋值型的那一版看不出问题。
  事件本身现在只发一次，正文在 `src/Fader.cs` 里 `Landed` 那一段。
- **写同一份 `keeper-probe.log` 的不是一份实施，是 `Probe` 和 `FadeRun` 两份**（`App` 写的是另一份）。
  当时以为「几份实施里只有一份带那两道保护」，实际更糟 —— **没保护的那两份写的正是同一份文件**，
  两次测量程序各写各的就在互相覆盖。
- **退出码要攥住句柄才读得到**：`Start-Process -PassThru` → `WaitForExit()` → `$p.ExitCode`。
- **`_console.exe` 是个壳**，真正的游戏进程是它的子进程：按名字停只停了壳，桌面留下 6 个还在跑的
  App（各自一颗托盘、同一个日志），实测结果因此串了两轮。要按 `Win32_Process` 找子进程停。登录项那条
  值同理要把壳换成同目录的窗口版，不然每次登录多一个控制台。
- **`Viewport.PushInput` 的传播顺序是文档写死的**：`_Input` → `Control._GuiInput` → `_ShortcutInput` →
  `_UnhandledKeyInput` → `_UnhandledInput`，前一个标了 `SetInputAsHandled` 后面不叫 —— 所以
  「`_Input` 数得到」从来不能当「控件收到了」的证据。**接 `GuiInput` 信号数事件，别重写 `_GuiInput`
  虚函数再叫 `base`**：跑的是 `Control` 那一份实现，`Button` 自己「点在我身上没有」那段根本不跑，
  于是每行 `Pressed=0`，量的其实是自己的测量程序。
- **引擎在发 `Toggled` 之前先改自己的状态**：只 `EmitSignal(Toggled, true)` 而不 `SetPressedNoSignal(true)`，
  「读格子上勾没勾」那一步就看不见这一发点击 —— 接线没错，是**发信号那一发不像一次点击**。同理
  `Range.set_value` 只在值真变时发 `value_changed`，`OptionButton.Select()`、`LineEdit.Text=` 都不发信号；
  灌值不回写走 `SetValueNoSignal` / `SetPressedNoSignal`。
- **`SpinBox.Value` 和里面 `LineEdit` 的字不同帧**：不写 `GetLineEdit().Text` 时自检里读到 `值 15、字 '0'`
  （`'0'` 是控件初始值）10 行一起报 —— 无头自检不开帧，所以**自检里的「字」永远是旧的**。
- **`QueueFree()` 掉的控件这一帧还在树里、还在收事件**：选一天重造整张格子会一层层叠上去（一发点击读出
  6 个 `gui_input`），换选中只许重画。同一族的方向反过来那一发是「新加控件的位置要等 3 帧排版」。
  拿 `GetChildren()` 的条数当屏上的条数也会在这里翻车（判据要剔掉 `IsQueuedForDeletion()` 的那些）。
- **`Root` 还在 `_Ready` 里排队装子节点时 `AddChild` 会被拒**（`Parent node is busy setting up children`），
  被拒之后那扇窗根本没进树，之后每一发 `push_input` 都是 `!is_inside_tree()`，**整张表读成「没点中」**。
  等一帧再挂，并且挂完自己报一次 `IsInsideTree()`。
- **排程序化点击，矩形要在开点那一刻读**，不能在排程那一刻读：`Enter()` 同一帧读 `GetGlobalRect()`
  拿到 `(1183,631)`，按钮真在 `(1280,903)`。先记成「新加控件要等 3 帧」，后一条把它纠正为读时机问题，
  同一轮又踩了一次。
- **测量程序的排程不能排绝对时刻**：扫桌面那一步里有 900 毫秒是睡着的，一次排到底后面的步全变
  「已经过期」，点击和它的实测结果挤在同一帧 —— 低级钩子在我们自己这条线程上回调、那一刻还没被叫到，
  读出来是「桥一发没喂」的假失败。改成「上一步跑完才排下一步」。
- **`Win32.ClickAt` 把 move+down+up 塞在同一批 `SendInput` 里，第一发会被格子吃掉**：计数加了
  （鼠标 按下=1/松开=1）、选中没换；先 `MoveTo` 把光标放过去、隔 400 毫秒再点才换选中。**测量程序多那一次
  移动不是产品的形状**，别把测量程序的形状读成产品的形状。
- **一行实测结果的位置也是实测结果的一部分**（用过三次）：印在后果之后的行会把后果安到上一发头上；
  `--shot` 第一版把 `AlphaMeasurement` 排在抓帧**之前**，而那条链要抬窗、要动 `GWL_EXSTYLE`，抓回来的
  「那一帧」是一张纯灰、连字都没有。
- **判据里那个「本来该是什么」不能从被测那一帧里推**：75% 遮罩底下压着 Chrome，拿本帧主色当基准，
  把桌面数成 34% 的「字」；换成「盖之前那一份 + 实测 alpha」才落到 1.95‰。**基准要么在磁盘上，
  要么在另一发里。** 屏幕上采到的像素与「桌面按 8 位 lerp 混 `#008040`@0.75」逐通道**差 0** 才是硬证
  —— 上一轮那条报 191 就是因为窗口根本没上屏。
- **「按 8 位混」那一问答的是纯色底，采样点上面就不许有控件**（2026-10-07 量到）：
  采样点原来按四分位取死点 —— 1/4 宽和 3/4 宽。3/4 宽那一点（2560 屏上是 1920,720）
  落在清单列里：清单默认占屏宽 62%~96%（`StepLayout.Default`），而那个框是满高、内容居中的，
  所以纵向正中那一带有没有字**取决于清单有几条**。实测读到 (207,231,219)，
  拿纯色底的期望值去比逐通道差 143。**红的是「那一点上有字」，不是混色错了** ——
  1/4 那一处差 0，混色实现本身对得上（`#008040` 那个底色）。
  **判据没坏，是取样点选错了地方**，而死坐标会随布局再变一次、再红一次。
  改法：采样点**向布局要** —— 把这一步每一个会画东西的控件的框躲开（外扩 16 像素，
  字是抗锯齿的、边会渗出框外），取离屏心最近的那个纯色底的点。
  **图控件路径为空时压根不画，不算**：默认布局里那个铺满整屏的图控件就是空路径，
  算进去就一处都找不着。**挑不出来时先红，不当绿** —— 期望值算出来是空列表时那一问会返回 0，那是假绿。
  改完实测：取样点 (1280,896)，避开了 5 个框，逐通道**差 0**。
  **顺带一条**：框从「按内容高度摆」改回「满高」之后，那一点上**仍然有字** ——
  那一改复现的是「今天这一屏的样子」，不是「那一点回到缝里」。两件事，别当成一件。
- **判据要两头夹**：`Measurement` 换成假值后叫一发 `_Process(1.2)`，标签必须出现 `12.3`；再叫一发
  `_Process(0.05)`，必须**不**出现 `99.9`（防它每帧刷）。自检里手动叫 `_Process` 不证引擎每帧会叫它，
  那半条靠帧数实测结果（`322 帧 / 5381 毫秒`）补 —— 分两处才是一条完整证据。
- **被认定「会被 X 骗」的判据，先别把 X 关掉，让判据学会 X**：那条 613‰ 一直是一个真 defect 在喊，
  隔一个半小时一句「这数是脏的、别看」差点把喊声关掉。
- **一支测量程序看不见的那件事，它的沉默不是证据**：逐帧比「字 vs 值」的测量程序对「60 从哪一帧来」完全无能
  （60 若在灌完之后写进去，字和值一起变 60，它就报 0）；换成只问「我这趟开始之前那一格里是什么」
  才切开。
- **测试资产长得像缺陷，就一定会被读成缺陷**：`image.file` 图省事指到仓库现成的日历截图，休息屏上
  出现放大 3.4 倍的桌面日历。中性资产要自己生成。
- **合成投递不带真输入，规则会正常工作**：预览一举起来就被 `Scheduler.cs` 的 `steppedAway` 收掉
  （`Activity` 读到的还是「静了 199 秒」），读起来像预览坏了。真手点那发留住了。
- **`--fader-shot` 落定那一发**：淡入途中鼠标动一下（第一步可挥散）遮罩就在抓帧之前没了，而它照样印
  「两帧都落盘了」，还顺手 `TogglePreview()` **又举起一扇**。
- **DPI 口径：虚化空间和物理空间不能跨着点**。DPI-unaware 的 PowerShell 里 `SetCursorPos` /
  `GetWindowRect` / 截屏是**一整套虚化坐标**（这台差 1.25 倍 —— `1689,1176` 和 `1351,941` 是同一个点），
  进程内读的是物理坐标；桌面是 2048x1152 物理而 Computer Use 给逻辑矩形，第一发因此点偏。
  **虚化空间里量就在虚化空间里点**；外部抓屏要先 `SetProcessDPIAware()`。
- **真点击的闸门是归属不是坐标**：外部 `SetCursorPos`+`mouse_event` 要把物理坐标 ÷1.25，并且**先让
  程序自己回一句「这一点归谁」**（`DesktopLayer.OwnerOf`）；那一次脚本是先打印再点、没拿
  `归自己=False` 当闸门，一发落在了别人的窗上。滚轮从别的进程发不进非前台窗（三次
  `mouse_event(WHEEL)` 一格没动，`WM_MOUSEWHEEL` 归前台那一家，**没单独证**），实测可用的一条是临时把
  窗口加高。
- **发键之前必须确认前台就是目标（认 pid）**：这台机器的记事本是商店版，`Start-Process notepad` 起的那个
  壳立刻退、前台还是别人的窗；上一版没设守卫，一串 `zhongqiu` 打进他 Chrome 那个标签页里了。
- **没人点的抬起、定时器开的窗拿不到前台**（`SetForegroundWindow=False 前台是我们=False` 而
  `输入框有焦点=True`），`HWND_TOP` 也压不住别人：要那一帧就得 TOPMOST，并把「命中是不是我们自己」
  写进测量程序（抓到过别人的 IDE 桌面和一份 markdown）。测量程序的输出路径要接全路径 —— 第一版按文件名拼，
  两只 PNG 掉进了工程根目录。
- **布局判据只该问横向**：整份表单在 `ScrollContainer` 里，纵向「伸出窗口」第一发读出 244 个 —— 那全是
  滚动区里的正常内容；横向伸出才是真坑。
- **要界面图走 `GetWindow().GetTexture().GetImage()`**：拿的是这扇窗自己渲染的那张纹理，不截屏、
  不要求它在最上面（被别的程序压着照样拿到 660x780）。`--shot` 那一路要先举窗、挪窗才截得对，
  那就是占屏幕的东西。
- **改桌面的测量程序要一条不骑在帧上的兜底还原**（另开线程 + 15 秒死线 + `Interlocked` 旗），否则
  「这扇窗不出帧」会把桌面永远留在最小化。还原对账那 1.5 秒窗口也不总够：有一回读「仍最小化 1 扇：
  `'Keeper - Godot Engine'`」，等不到、手工 `SW_RESTORE` 才回来 —— `UndoMinimizeALL` 是异步的，
  补 Sleep 之后仍读到过一回。
- **测量程序不许在别人下次登录里种进程**：带 `--data` 的一跑默认**跳过**注册表那一步，要真验得明说
  `--registry`，日志会写清楚（`测量程序跑，注册表没动`）。跑法：
  `--path . res://src/App.tscn -- --options --data <临时目录> --seconds <n> [--registry]`。
- **「凝实」和「进 step 2」谁先到不固定**（同轮差 30~80 ms，两个方向都出现过）：斜坡按帧推、
  step 按 0.2 秒一步推。凡是挂在其中一件事之后的实测结果都得扛另一种顺序。
- **PowerShell 两个**：5.1 的 `Add-Type` 是 C#5 编译器，`=>` 成员写法过不去；给 `string` 参传 `$null`
  会换成**空串**，于是 `FindWindow('KeeperTray', $null)` 报 0 看着像「按类名找不到」，真 NULL 要
  `[NullString]::Value`（类名是小写敏感的，`'keeper-tray'` 报 0）。
- **数托盘图标要用 UIA 走 `Shell_TrayWnd` 并且把隐藏区展开**（`TopLevelWindowForOverflowXamlIsland`
  关着的时候里面那些根本不在树上）；那一发自己会被「别的窗抢到前台」关掉，所以「0 颗」有可能读的是
  没展开的桌面 —— 走过的节点数从 ~480 掉到 452 就是它关了的信号。
- **出口现场那两跑的跑法是算出来的，不是试出来的**：step 1 的长度是 `max(step.ms, fadeInMs)`
  （`Scheduler.StepMs`），所以能被挥散的窗口只有淡入那 3 秒；`wavedAway` 认的是
  `BusyMs(StepAtMs) >= dismissHoldMs`（2000），而 `BusyMs` 在 `IdleMs > BurstGapMs`（1000）时直接归零 ——
  抖动的间隔必须小于 1 秒，5 秒一下的那种「连续」不起来 2 秒；翻倍那一档要在 60 秒的重试等待期间保住
  streak，因为 `ContinuousMs` 在 `IdleMs > StreakGapMs`（60000）时归零、**而归零那一步顺手把 `Skipped`
  也清了**（`Scheduler.cs` 里 `ContinuousMs` 归零那一段）—— 干等 60 秒不动鼠标，第二次根本不会起来，
  起来也还是 60 秒那一档（B 跑中间那 55 秒的 `keep` 就是为它存在的）。两个不奇怪的实测结果：
  `--jiggle 24` 之后淡入在 25 秒（raise 要 `triggerPauseMs` 那 1 秒的静）；「静了 9 秒才落进来」正常，
  三个条件谁先满足不影响抬起。

  **2026-10-21 之后这段读数的前提变了**：触发不再看 `ContinuousMs`，
  改看「这一段从哪一刻起算」（`Scheduler.SegmentStartMs`，现实时间）。
  上面那些跑法仍然照旧能测「挥散 / 提前结束 / 记不记」，
  但「干等 60 秒让它归零」现在不再压住触发 —— 那一段照样走到线。
  机制在 [`../design/detection.md`](../design/detection.md)「倒计时和触发按现实时间走」那一节。

- **注入的 Escape 一次干两件事**：撤了菜单**也把设置窗关了**（`_UnhandledInput` 那条 Esc）。下一发想用它
  验「关掉不保存」之前，先想清楚这一杆枪打的是哪只鸟。
- **一发触屏只发一次 `ButtonUp`**，套一层 `Control` 也一样 —— 所以「一次点击两下」不是引擎重映射，
  是两路事件（OS 投递 + 钩子喂）叠出来的。

- **临时区里那几十个 `keeper-*-selfcheck-*` 目录，是历史遗留不是活的泄漏**（2026-10-05 量到）。
  数量看着吓人（量到过 80 多个 `keeper-screen-selfcheck-*`），而**改完跑一次自检，新留下的目录是 0**。
  时间戳是判据：最后一个孤儿的时间戳早于补上 `DropDir` 的那一发，那一发之后就没再攒过。
  **这一条是「先量再下结论」的一次**：那份架构复核报告第一版把它当成「九份收尾各写各的、
  已经坏了」的证据写进去了，而它量的其实是修好之前的那一段历史。**孤儿目录能当证据用 ——
  但要先问它是在修好之前攒的还是在修好之后攒的**，而唯一能答这个问题的是时间戳，不是数量。
- **词表是手写的，判据就只量了它写下来的那一类**（2026-09-30 晚，设置窗「界面上不许出现
  配置文件内部的名字」那一条）。那张清单当时只有五个词（`modes` / `stage` /
  `settings.jsonc` / `毫秒` / `ms`；**这两个词后来改成了 `flows` / `step`，这一段记的是改之前那一版**），自检全绿，而界面上原样摆着 `wallpaper` `outline`
  `widget` `marginXPercent` `marginYPercent` —— 五个都在 `calendar.style` 和
  `calendar.corner` 那两条提示里。**症状和「检查没跑」一模一样**：绿，规则被声称成立，
  而它只对清单里那几个词成立。判据说「界面上不许出现 X」而它实现成「界面上不许出现这五个」，
  中间那一段没人管。
  **词表要能从它描述的那个东西派生出来**：声明表是唯一知道「配置里有哪些词」的地方，
  所以名单从那里来（每一条键的点分段 + 每一条 `Choice` 的取值 + 文件名/那张表的键/字段名）。
  派生出来立刻多报 11 条 —— 其中 9 条是真漏，2 条是**值该露面的地方**（`flow` 那个下拉里
  摆的就是休息流程的名字）。所以名单还得分两档：**结构名**（键、文件名、字段名）到处都查，
  **取值**只在下拉里那一项以外查。**用户自己的数据**（休息流程名，能改能删能新建）两档都放过 ——
  内置那三条恰好叫 `fadetop` / `todoList` / `pomodoro`，和它们在配置里的键同名，
  但用户新建一条叫「喝水」也得能摆在那儿。分档的依据是 `OnScreenText` 报的那一位，
  不是某个路径白名单。
- **子串匹配出来的红要当假的看**：`ms` 用 `text.Contains` 去撞，`forms` 就会红。判据里凡是
  「这个词不许出现」而这个词又是常见英文的，一律按**整词**切（`Tokens`），中文那种没有词边界
  的才退回子串。
- **改完要反向验一次这条判据还会不会红**：把 `headerPercent` 塞回 `calendar.headerPercent`
  那条提示，当场就报「Text/Hint 的文字里有「headerPercent」」—— 不验这一下，新判据有可能
  是个恒真的空壳（`Walk` 走空、或 `OnScreenText` 认不出新控件类型，实测结果照样是绿的）。
- **判据要在它声称覆盖的那一档上真的跑过**（2026-09-30 晚，接着上一条）。派生词表在
  **中文**那一遍是准的，于是「界面上不许出现配置文件内部的名字」绿了半年 —— 而那一遍
  **只跑中文**。打开英文那一遍之后，一口气报 **28 条**，逐条看过**没有一条是真的**：
  `stretch`（"one focus stretch"）、`sound`（"Plays the sound"）、`file`（"Picture file"）、
  `volume`（"Playback volume"）、`corner`（"Which corner"）、`calendar`
  （"Keep the calendar on the desktop"）、`wallpaper`（"against the wallpaper"）。
  这些在英文正文里就是**普通词**。所以两门语言的名单必须不一样：中文查全份
  （正文里不夹英文词，出现在那儿只可能是被引用了），英文只查**有辨识度**的名字
  （带大写字母/数字/非字母字符的：`marginXPercent`、`fadeInMs`、`settings.jsonc`）。
  **代价要一起记**：英文正文里引用一个**纯小写**的名字（`The widget`）那一遍查不出来 ——
  那是覆盖不到，不是它干净。要补那一档只有一条路：给纯小写的名字配一份「它在这门语言里
  是普通词」的名单，那又是一份要人维护的清单，所以没做；那一条是**读出来的**不是抓出来的。
  顺带那 28 条里**混着两条真的**（`marginXPercent` 和 `The widget` 都在英文文案里），
  所以「这一遍全是假的」也不能当通例 —— **得逐条看过再下结论**。

## 「零读者 / 有重复 / 谁在写」这类案头判断，落笔前要直接读一次

这一族不是测量程序的坑，是**人坐在案前数的结构**。三条都是当轮被直接实测结果打回的，记在这儿当反面实测结果。

- **`SettingsStore.Read.Text` 不是「外部零读者」**：`Probe.ReadLiveDocument` 拿它数文档里有几个键。
  那句「零读者」是**注释**里写的（注释说它是「原位编辑的底稿」，而 `Save` / `Export` 各自重读磁盘，
  那是有意的 —— 底稿要是在内存里这一份，别处改过文件就会被悄悄盖掉），字段本身留着，注释改准了。
  **数读者要看调用点，不是读注释。**
- **「这一块屏的矩形」不是重复实现**：`App.ScreenRectOf` 还 `Rect2I`（喂 `ScreenGetImageRect`），
  `Wallpaper.MonitorRect` 还 `Win32.Rect`（算壁纸摆位），Fader 和 FadeRun 用引擎那一对 `Vector2I`。
  同一个问句、两种答案类型，各自都是它那个调用方的自然形状 —— 硬收进一个模块是**加转换**，不是去重复。
  `Screens()` 那两份的差别也是有意的：FadeRun 那一份还要求命令行上有 `--all`，测量程序不该不带旗就盖满每块屏。
  这一族没收。
- **两份实施写同一个文件，比「一份有保护一份没有」更糟** —— 上面那条 `keeper-probe.log` 就是。查的时候
  要连「谁在写」一起问，光查「有没有保护」会把最坏的那种漏掉。
## 一次 `SendInput` 交三发，低级钩子会把「按下」那一发丢掉（2026-10-10）

`Win32.ClickAt` 原来把**移动 + 按下 + 松开**塞进**同一次** `SendInput`。

**量到的读数**：`SendInput 交了 3/3 发`（系统全收了），而同一进程那一把 `WH_MOUSE_LL`
读到的是 **「移动 3、按下 0、松开 1」**。第二发点同一族（点那颗钮）读到的是
「移动 3、按下 1、松开 1」—— **两发用的是同一个函数、同一批标志，差的是时机**。

**为什么它危险**：这一族要问的那句话是「钩子吃没吃」。按下那一发丢了，
`MouseSwallower` 压根没被问到，于是读出来是「没吃」——
**而真相是「没问」**。答出来的读数完全合法，看不出任何一处坏了。

**修法**：三发分三批交，每批之间 `Thread.Sleep(40)`。修完同一发读数变成
「移动 3、按下 1、松开 1」，清单第一格当场勾上。

**和这一族同族的近邻**：「控件树来不及进「按下那一档」」是同一件事在 GUI 那一侧的样子
（记在 `docs/research/desktop-layer-and-window-measurements.md` 那张坑表里）。
两边都记着，是因为它两次都表现为「发出去的没全到」，而量具报的是「没反应」。

## 判据要问的东西，得看**站在哪一刻**问（2026-10-10）

`FadeRun` 的 `Passthrough` 原来有两问，第二问是「这一步收鼠标，那一块就该非空」。
它被三处调用，其中一处是**淡入中** —— 那时还没落定（`Settle` 没跑），那一块当然空。
**判据当场报红，报的是「0/1 块屏那一块非空」，而产品那一侧一切正常。**

**量到的对照**：修完之后同一发在「淡入中」答 `0/0`（该是 0，它就是 0），
在「落定之后」答 `1/1`。

**修法**：`Passthrough` 多收一个 `afterSettle`，「非空」那一头只在落定之后问，
而且只在**这一步声明收鼠标**的时候问。「那一块上不许有我们的窗」那一头**不落定也问** ——
它量的就是有窗那一版的病，什么时候都该成立。

**为什么这条要单记**：报红的那句话里没有一个字是假的，量到的数也是真的，
而它指的不是产品坏了 —— 是**判据站错了位置**。这一族已经栽过两次同样的形状
（`RowsInside` 那个假阳性、工单 02 那个 1×1），三次的共同点是：
**「量具不量这个」和「量具量错了时刻」在读数上长得一模一样。**

## 独立测量程序那一族：判据自己要先量得对（量于 10-12）

模块在 `src/tools/DebugProbe/`（另一个工程，不开引擎），工单在 `.scratch/debug-tool/issues/`。
这一族是照着「量具坏了而机制没坏」那三次栽跟头造的，所以**尺子自己的判据占了一半**。

### 「两片取自同一张图」要落在类型上，不是落在注释里

这一族栽过的三次里有两次栽在**基线**上：拿「藏起来那一帧」当基线（读到纯黑，
那是 Explorer 没补画，和「本来就没画出来」是同一个数）、拿「另一档」当基线
（两帧都被同一扇窗盖住，逐像素读出「0 个不同」，那意思是「都被盖住了」）。

所以取片的那个方法**签名里只有一张图**：

```
internal (int Inside, int Total, int DistinctOutside) CountNotIn(Frame frame, RectI inner, RectI outer)
```

两片各自给一个矩形，**没有第二个 `Frame` 可以传进来**。跨帧比较和「藏起来那一帧当基线」
这两种读法在这一个签名下都写不出来 —— 不是靠人记得不这么做。

### 这把尺子自己的对照（`shot --check-diff`，不需要干净的桌面）

| 对照 | 外片放在哪 | 读到的命中 | 该是什么 |
| --- | --- | --- | --- |
| 一 | 压在内片自己身上 | 0 格 / 46048 种颜色 | 零命中，判「没画出来」 |
| 二 | 同一张图上另一段（`(1560,0)-(2340,1050)`） | 482008 格 / 9 种颜色 | 有命中，判「画出来了」 |
| 确定性 | 同一张图上数两遍 | 读数一模一样 | 一模一样 |

**这一发不靠「屏幕上正好是干净的」** —— 那一带有没有内容不要紧，
要紧的是同一张图上把外片挪来换去，命中数按预期变。

### 「谁压着谁」三档之外还有第四档：系统窗

命中测试原来分三档（归日历自己 / 归壁纸层 / 归别家窗）。**头一版把任务栏算成了别家窗** ——
`Shell_TrayWnd` 那一族本来就排在桌面上面或下面，压不到内容，
它一被算进污染，日历矩形下缘那一带永远拒收。

第四档叫「归系统窗」：任务栏那一族 + 输入法那几个辅助窗。
**它既不是「露到壁纸」也不是「被别家窗挡住」** —— 混进前两档就是把两件不同的事说成一件。

### 判据照抄产品那一侧的名单，不自己另列一份

`Shell_TrayWnd` / `ApplicationFrameWindow` / `Windows.UI.Core.CoreWindow` / `IME` 这一族
是照 `src/DesktopLayer.cs` 的 `SystemWindows` 抄的，**两处不许各列一份** ——
各列一份的话，下一次改了一处，另一处就会开始把系统窗当污染报出去。
