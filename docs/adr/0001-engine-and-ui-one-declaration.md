# 选型、界面、语言：一切从同一份声明来

**这一张并了原来的 7 张：ADR-0001 到 0007**（2026-09-29）。下面每一节是一条取向 —— 定了什么、否了哪条路、代价是什么。程序该做什么在契约，实测结果在 `docs/research/`，复核要照的规矩在 `CODING_STANDARDS.md`，这张不重述它们。

## 引擎用 Godot（mono）+ C#

要的是：一扇能常年站着、能压满每块屏、能挂进壁纸底下、能画到像素的窗。引擎那侧给得了每像素合成、帧驱动的斜坡、真控件和主题；剩下的一半是 Win32 —— 托盘、判断你有没有回到工作的输入钩子、把窗挂进壁纸、独占全屏探测、登录项、JSONC 的原位写回。C# 里每一条是一行 `DllImport`；GDScript 里每一条要一个 C++ 或 Rust 的 GDExtension，等于后端建两遍。mono 版已装好，选 C# 不产生安装成本。常驻那一份底座实测结果在 `docs/research/godot-footprint.md`（199 MB / 2 个进程，本机的）。

**否掉的**：原生 Win32 + 自绘界面（等于把界面层重写一遍）；以 GDScript 为主（后端两份）。

**这不是「禁用 GDScript」**：挂在场景上的小脚本、编辑器侧的临时试验直接用，汇报里说清选了哪个、为什么。

## 不建 schema 链，界面在编辑器里搭成场景

取向：**一个限制只声明一次**，界面、恢复默认、夹取、首启文档那几个读者读同一份声明（声明表在 `src/Settings.cs`，读者清单在契约）。中间不隔一层 schema，也不隔一层「生成出来的类型文档」—— 那些产物的存在理由通常是「得把范围递过一条进程或语言的边界」，而 Keeper 里设置、界面、字符串表都在同一个进程，一次方法调用就到，没有边界要递，产物也就没有读者。

Options 窗和其它 Godot 界面一样由 `.tscn` 摆位置，控件上只写 setting 的键名，`_ready()` 时从声明表取值 —— 场景里因此不出现第二个数字。

**一条通则，定死在这一节**：滑块拿声明表的上下限，**数字输入格只拿下限、一律不封顶**，上限只在写回那一步管。把上限抄到控件自己身上，代价是「打一个超出范围的数，屏幕上先变成一个你没写过的数」那一帧（他真鼠标点出来的那一条）；自检里 options 那一组断言着这一句，所以代码不会悄悄改回去。

**否掉的**：运行期用代码拼整窗界面（一扇窗就两份真相：场景一份、代码一份）；把范围抄进场景（声明表就有第二份）；给编辑器导出一个 `.json`（那是加功能，不是打地基，真要做也从同一份声明导出）。

## 界面默认用真控件，托盘菜单不 owner-draw

`Label` / `Panel` / `CheckBox` / `GridContainer` + `Theme` 摆得出来的就用它们；自绘只留给控件确实画不出的那部分（比如贴着壁纸的那种细线格）。代价一条：**自绘换来的焦点、命中、主题、DPI 缩放全得自己管**，而恰恰是能点的那一段最要点得动。托盘那一侧同一句话 —— 普通字符串菜单项就够，菜单上全是文字，没有自绘的理由。引擎没有托盘 API 这一点不因此改变：`Shell_NotifyIcon` + `TrackPopupMenu` 还是得 C# 调，那是**调用**，不是自绘。

**否掉的**：自绘托盘那几项、自绘整窗 —— 换来的只是外观。

## 设置窗的主题是两份独立文件，生成脚本已经完成使命

`src/Theme_light.tres` 和 `src/Theme_dark.tres` 是**同一份模板、两个调色板**。手抄的话暗色那套就是亮色那套的第二份真相：加一个控件状态要改两处，漏一处就是「默认件在暗底上更刺眼」那一种难看。

**为什么是两个独立文件而不是场景里的 `sub_resource`**：设置窗要按 `uiTheme` 那个键在运行期换挂整张主题（设计文档 `docs/design/config.md`「设置窗的配色是一个键」，默认亮色），而 `sub_resource` 只能从场景里按名字刨出来 —— 挂在场景里的主题没法「按路径加载再换上」。拆成两个 `.tres` 之后换主题就是一句 `GD.Load`，两份各只有一份，场景里只剩一行 `ext_resource`。

这两个文件当初由两个一次性的 Python 脚本生成：一个出那两套主题，一个批量改设置窗场景的版式。脚本完成使命之后，2026-10-08 从版本库清掉了。**理由是过期的生成脚本留在版本库里比没有更坏** —— 改场景那一个走的是「替换整段」而不是幂等的，照着它文档里写的那条重跑命令跑一遍，会把现役 `Options.tscn` 之后的全部改动覆盖掉。**正本是场景和那两个 `.tres` 本身**，取向仍然是「不建 schema 链，界面在编辑器里搭成场景」那一节写的那样。同族那几个备份文件（`Options.tscn.bak`、`Options.theme.bak`）一起清掉了。

## 拖放走引擎的虚函数，刻度线和改大小手柄自己画

遮罩那一屏要有一个用户自己拖的布局编辑器（契约
`docs/design/fader-layout.md`「遮罩的布局是每一步自己那一份」那一节）。这一节答的是那一扇窗的
三样东西里，哪一样引擎给、哪一样要自己写。

**引擎给的**：拖放那三个虚函数和 `SetDragPreview`，4.7 仍有效、没有废弃。
**本机实测结果（2026-10-06，`docs/research/godot-drag-and-snap.md` 第八节）**：
**源侧落侧都走得通** —— `_GetDragData` 和 `SetDragPreview` 各 1 次、`_CanDropData`
3 次、`_DropData` 1 次，拖动中 `GuiIsDragging()` 为 `True`，`at_position` 是控件内的
点而不是 `INF`。

**喂法是这一族的关键，两条都要照做**（都在那一发里踩过）：
1. **喂系统那一层**（`Win32.SendInput`，走窗口消息那条路），不是引擎的 `PushInput`
   —— 进程内喂进去的移动走不到落侧。
2. **分段交，段间让帧**：按下 → 逐格挪 → 松开。一次把十几发全交进去，全在同一帧
   里进去，GUI 的拖动状态机来不及进「正在拖」那一档，连拿起那一发都读不到。

**引擎没给的**：刻度线（吸附参考线）和改大小的手柄，两个都没有 ——
`Control`、`Node2D`、`CanvasItem`、`GraphEdit`、`Window` 五个类搜下来零命中。
`GraphEdit` 那个 `snapping_enabled` 是节点图连线吸附，不是画布对齐。
手柄要在 `_GuiInput` 里自己判事件落在不在边上。实测结果和签名在
`docs/research/godot-drag-and-snap.md`。**刻度线和手柄命中两族「自己算得出来」**
已由那一发验过（门限内吸得住、门外不吸；边带命中和矩形内命中分得开）。

**`gui_snap_controls_to_pixels` 不用拧**：它默认开着，但**实测结果是拧它对
`Control.Position` 没有任何影响**（三档读回全是 `100.4`）—— 那一层只作用在引擎
自己排版算出来的矩形上。理由因此改掉：**不是「拧了才干净」，是「拧了也不一样」**。

**键盘发起的拖动在 C# 侧没有入口**：文档说那条路 `at_position` 是 `Vector2.INF`，
但这一版 C# 绑定里 `Viewport.AccessibilityDrag`、`SetDragForwarding`、`ForceDrag`
三个方法**反射都查不到**（只有 GDScript 那一侧有）。所以那一条命中判定的分支现在
是一处待分支的约定，不是一处真会发生的路径。

**代价**：自绘换来的命中和 DPI 缩放全得自己管 —— 上一节那句话在这里原样成立。
编辑器是这一族里自绘最重的一扇窗，控件本身的焦点、主题、命中仍然走真控件，
自绘的只有那几条参考线和那几个手柄。

**没定的**：官方没给指引的那一条**已经被本机实测答掉了**（2026-10-06 第三发
`--canvas`，见 `docs/research/godot-drag-and-snap.md` 8.7）：**画布是真 `Control`，
子控件是真 `Panel`，`_Draw` 只画上面那一层**；引擎重排（挪子控件、换画布尺寸、
不主动 `QueueRedraw`）四种读数下自绘那一层**都在**。

**拖动过程中那一档要自己 `QueueRedraw`** —— 量到的是「不主动重画时上一次画的还在」，
**不是「位置自动跟着变」**，后者要代码自己算。

**否掉的**：拿 `GraphEdit` 当画布（它是节点图，连线语义不对）；用
`gui_snap_controls_to_pixels` 当刻度线（它只舍到整像素，不认别的控件在哪）。

## 语言表：一张 CSV 自己解析，编译期那道保证换成自检里一组

`locale/keeper.csv` 由 `src/Lang.cs` 在运行期自己解析成引擎的 `Translation` —— **不走引擎的 CSV 导入**：那条路要编辑器先跑一遍 import 才有 `.translation`，而这一侧每一条判据都要在无头里跑得动。场景和原生的托盘菜单、窗口标题都从 `Tr()` 取，所以不必养第二份表；托盘菜单和标题是原生的，换语言时要重建它们。

「少一条翻译」这一类错，靠的是**自检里 `lang` 那一组**：任何键缺 zh 或 en 就非零退出。

**这条比编译期那道硬保证弱**，要不可绕过就得走代码生成（从表里生成一个键的枚举，让缺一条编译不过）—— 那正是上一节否掉的那一类中间产物，所以不往那条路走。（`locale/` 下那两个 `keeper.*.translation` 是引擎导入留下的产物，没有读者，别拿它们当「走了引擎导入」的证据。）

## 术语：用圈内既有的那个说法，不自己造、不按字面译

名字只有一个来源：**已经在用的那个说法**。圈内是中文就写中文（`遮罩`、`实测结果`、`取向`、`工单`），圈内只有英文就原样写英文（`seam`、`stamped`），两边都有就取更贴的那个 —— 不新起第三个。名字还要过一条硬下限：拿到它的人能靠它把一件事说清，**且只有一种读法**；「模式」那种直观、却被两个概念抢的词过不了这一关（契约里记着它撞的那三回）。

**「翻译」是个错的靶子**：错的不是译成了中文，是那个词不在圈内。`tickets` 在这一行里叫**工单**，不叫「票」；`seam` 在这一行里没有中文名，就写 `seam` 原词，别造「戳」。2026-10-01 清掉的那三个自造说法能给这一条作证：「戳」当时指的是 `schemaVersion`，现在叫**格式版本**（也是中文），一起清掉的还有判据的「牙 / 反向验牙」（现在叫**判据能失败 / 不会失败**和**反向验证**）。同一个词在语言表英文那一栏照旧写 `stamped`，没动 —— 这条规矩不是中英之争。

**2026-10-05 清掉的两个词，是同一类里第二大的那一件**：`量具` 和 `读数` 各有 300 余处，散在源码注释、`docs/`、`.scratch/` 工单和临时脚本里。它们两样硬下限都不占 ——「量具」是计量学的行话，「读数」是仪表盘上那个刻度，拿到词的人不会想到它指的是「探针跑出来的那一行结果」。**换法同样是不另起名**（所有者 2026-10-05 定夺）：`量具` 改成**测量程序**、`读数` 改成**实测结果**，代码里 `Reading` 改成 `Measurement`、`*Reading` 那一族方法同改，三个带 `readings` 的研究文档改成 `measurements`。**一起清掉的还有「探针」那 58 处** —— 它和 `量具` 本来就指同一批东西，仓库里两个词并着用；现在全仓库只留**测量程序**一个。**没动的是别的词** —— `量`、`测量`、`测量值`、判据、基线都留着：清掉的是这两个词，不是含「量」的那些字。

**可核对的那一半**：新说法落 `GLOSSARY.md` 一条，连 `_Avoid_` 一起；**词不在词汇表里却渗进代码和文档，那不是术语是行话**（2026-10-01 那一发的原话）。

**2026-10-02 清掉的那一个字，是这一类里最大的一件**：`--check` 那次无头自检在 `GLOSSARY.md` 里叫过「门」—— 散在 `CODING_STANDARDS.md`、`docs/`、`.scratch/`、源码注释里 500 余处。它两样硬下限都不占：读起来像「闸门」或「入门」，而改之前那些「门里造得出事件」「绿色的门不是验收」的句子，谁也读不出它指的是哪一次跑。**换法是不另起名**（所有者 2026-10-02 定夺）：文档一律直说「跑一次自检 / 自检里 / 自检全绿」；`src/Gate.cs` 改成 `src/SelfCheck.cs`、类名 `SelfCheck`；英文散文和日志串里的 `gate 1/2/3` 改成 `check`。**没动的是别的词** —— `专门`（普通副词，不是术语）、鼠标桥那个 `闸门`（命中测试开不开，与自检不是一件事）都留着：清掉的是这一个概念，不是含「门」的那些字。**2026-10-06 又清掉两个**：`门限` 换成直白说法「差多少算「对上了」那个数」，不再给那个概念起名；`门槛` 换成 `边界` 和「「你回来了」那一条线」—— 仓库里三处「门槛」用的全是「标准线」那个义，没有一处是「阈值」那个义，而上一句豁免写的偏偏是「阈值那个义」。`GLOSSARY.md` 里「判据」那条的 `_Avoid_` 仍列着 `门槛`：那是禁用清单，不是用法 —— 留着它是为了防止同一个词再被写回来。

**否掉的**：按字典直译（`tickets`→票）；同一件事中英各留一份（两处一定会漂移）；拿隐喻当术语（说不清验收是什么）。

**2026-10-06 清掉的两个词是这一类里最小的一件，但也是唯一一件先证了「圈里没有」的那件**：`时间线` 和它里面那一步的 `段`。**取证那一半**：`fadetop.com` 自己的词只有 Activity timeout / Fader / Break Trail / Health Index，它压根没有「一份带几步的休息」这个东西 —— 所以这一对**不是不按字面译，是圈里压根没有现成说法可抄**，换法只能另起。**为什么非换不可**：`时间线` 在日常中文里读成历史事件的时间轴，而 Keeper 的是一份带名字的配置；`段` 更糟，它指着三件事 —— 流程表里的那一行、一段时间（`休息段` / `专注段` 的原义）、以及完全无关的 `时段` / `片段` / `段落`。所有者 2026-10-06 定夺：`时间线` → **休息流程**、表里那一步的 `段` → **一步**。**一起改的还有代码和配置**（照 2026-10-02 那次 `Gate` → `SelfCheck` 的先例）：类 `Mode` → `Flow`、`Stage` → `Step`，配置键 `modes` / `mode` / `stages[]` / `blocks[].timeline` → `flows` / `flow` / `steps[]` / `blocks[].flow`，界面文案跟着换（英文栏从 `Stretch` 改成 `Step`）。**顺手拆清的是那一处重载**：`休息段` 和 `专注段` 在 `GLOSSARY.md` 里各自加了一句「这里的段是一段时间，不是休息流程里的一步」，那两个字从此只指一段时间。**没动的是别的 `段`** —— 2164 处普通散文的「一段时间 / 一段话」、170 处 `时段` / `片段` / `段落`：清掉的是这一个概念，不是含「段」的那些字。**躲开的六个同名**（一个都没跟着改）：托盘那枚 `Tray.Mode` 枚举、壁纸的 `Wallpaper.Mode`、`stretch mode`（引擎属性）、Win32 里的 IME 档、`LifeModeIndex.LegacyFolderName`（生活模式的老目录名，它也叫 `modes`）、自检的禁用词表。顺带修掉一处真重名：托盘钩子上那个 `Modes` 字段装的是**生活模式名单**，和设置窗的「时间线」分区撞了字，现在那个字段叫 `LifeModes`。

**这一件和前几次有一处不同，要单记**：**配置键改了，没有迁移那一层**。旧的 `modes` / `mode` / `stages[]` 读不进来了，而 `schemaVersion` 没有动 —— 也就是说别人机器上已经写好的那一份会**静悄悄**退回内置那三条（陌生的键是零代价地放过的，代价落在用户看得见的地方）。这是所有者明知道后果仍然选的换法（2026-10-06），记在这儿是因为它有代价，而代价不在代码里。
