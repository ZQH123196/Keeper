# 检测只感知，勿扰在业务那一侧

2026-10-04 所有者定夺（起因：把散着的输入检测、独占全屏避让扶正成一个检测模块，再围绕它做勿扰、自动暂停那一族任务）。产品行为在契约；那一族的形状在 `docs/design/dnd.md` 与 `docs/design/detection.md`，术语在 `GLOSSARY.md`「检测与勿扰」那一节；这张卡只装取向、被否的路和代价。API 取证（网页一手来源）在 `docs/research/detection-module-api-survey.md`，本机 Probe 实测结果在同那份的 1.1、3.1 两节（2026-10-04 量）。

## 模块只出实测结果，政策在消费方

**取向**：检测回答「现在是什么」——输入三问、独占全屏吗、前台应用是谁——不发「现在能不能打扰」这一类裁决。翻倍、让位、静默、不补那些全在消费方。

**否掉的：模块输出统一「能不能打扰」位。** 同一个独占全屏实测结果底下压着三条互不相同的政策：番茄钟「全屏一让就抬」、作息表到点「错过不补」、自动淡入「不记账也不补」。合成一个位，三条差别被压扁；要恢复就得在模块里给每个消费方开政策口子——那不是低耦合，是把政策搬了个家。

**否掉的：条件求值进模块。** 勿扰要读用户配置（时段表、exe 名单），那不是感知，是业务。放进模块，模块就得认识声明表和配置那一族——感知层从此有一条通向磁盘的路。

**代价认下来**：将来每个任务侧消费方要自己把实测结果拼成判定。第一个拼的是勿扰。

## 勿扰是业务功能，不是检测的一部分

**取向**：勿扰拿检测的实测结果和自己的配置求值，交一个「勿扰中，因为哪条」给消费方。它是检测模块的第一个验收消费方——「用来检查检测模块效果的」正是这个意思：实测结果好不好用，勿扰用一遍就知道。

**否掉的：勿扰进模块**（见上一节）；**否掉的：消费方各自求值**——Scheduler 和将来的任务各自读名单读时段，同一套规则写两遍，先过期的那一份不说一声。

**术语**：勿扰是圈内词（Workrave、Stretchly、SafeEyes 都用 Do Not Disturb / 勿扰，见 survey 第 5 节）。检测那一个统称**圈内没有**，所有者定夺用「检测」，已落 `GLOSSARY.md`。

## 前台取数搭现有轮询底盘

**取向**：App 那一侧 0.2 秒一发顺路取前台进程身份并求值勿扰。`GetForegroundWindow` 那一发本来就在问，加一次 `QueryFullProcessImageNameW` 是零分配快调用。Stretchly 在 Windows 上同款（进程名 + 轮询）。

**否掉的：SetWinEventHook 事件那路。** 要专线程 + 消息循环，且有已知的迟到、最小化双发、锁屏后失灵一族坑（survey 第 2 节，都带出处）；这些坑在这台机器上一发实测结果都还没有——实测结果不足的路不走。200 毫秒延迟对「勿扰 / 静默」用途无感。欠账里留着，实测结果先行。

**否掉的：轮询 + 事件双路对账。** 圈内确有人这么做，但对勿扰用途是过度设计：买即时性，付一整条专线程和一族未实测的坑。

**2026-10-07 补（范围变了，取舍还没翻）**：所有者把这一族定成这一版要做 ——「前台变化走事件」是契约的用户故事 100，工单 `18`/`21`。**上面那两条否掉的否的是「在没有本机实测结果的时候选它们」，不是永远不许走。** 现在三条路都开着：纯事件、双路对账、维持纯轮询；实测结果（延迟、双发漏发、锁屏往返、提权前台）出来才定，机制定了再改这一节。
**「模块只出实测结果，政策在消费方」那一条不受影响** —— 它划的是边界，不是路线；这一族范围变大不越过它。

## 应用认人用 exe 名

**取向**：匹配键 = 可执行文件名，整名精确匹配、大小写不敏感。跨安装位置稳、用户读得懂；实测结果里印完整路径供核对。同名冲突（`chrome.exe` 全家一个名）认下来——名单是用户自己写的，写的人知道自己的 chrome 是什么。

**否掉的：全路径当匹配键。** 挪一次安装、升一次版，名单全体失效；用户视角是「莫名其妙失灵」。
**否掉的：窗口类名。** Workrave 那一族的老路；稳，但用户读不懂，配名单等于配密码。
**否掉的：自动判「这是游戏」。** Windows 没有「这个进程是游戏」的 OS 判据；`QUNS_RUNNING_D3D_FULL_SCREEN` 社区实证只认 D3D 独占那一型，全屏游戏反而回 `QUNS_BUSY`（survey 第 3 节）。判别器产不出可靠实测结果——「游戏」就是名单上的一行，不是一个探测器。
**Stretchly 的子串匹配不抄**：它官方文档自己列了误伤坑（survey 第 1 节）。

**代价认下来**：MSIX 执行别名（`wt.exe` 那一族 reparse 点）和 UWP 前台窗归 `ApplicationFrameHost` 的事，exe 名这条路盖不全——UWP 解析和 CoreWindow 交叉点进 Probe 工单，实测结果出来再定接不接。

## Scheduler 收每帧组装的聚合

**取向**：Scheduler 面对一个聚合类型（三问 + 独占全屏 + 前台应用 + 勿扰中，带原因），类型住在 Scheduler 旁边（`Input` 同款：消费者定形状，生产者来实现）。App 每帧拼它：实测结果来自检测，勿扰位来自勿扰。政策全留 Scheduler——它拿聚合和 settings 的钥匙合成行为，和今天 `blocked` + `blockWhenFullscreen` 同款。

**否掉的：散参数再加一个。** 参数到六个，每加一种实测结果动一次全仓签名。
**否掉的：模块推事件、Scheduler 订阅。** 「假时钟一帧帧推」那套自检是契约级手感规矩唯一的证法，事件驱动会把它拆掉。

**搬家不动实测结果**：Activity 原封搬入，`Input` 接口、MouseBridge 旁路、`FakeInput`、既有自检全零改动；Fullscreen 搬入，判定照旧。谁借搬家顺手改实测结果，自检当场报。
