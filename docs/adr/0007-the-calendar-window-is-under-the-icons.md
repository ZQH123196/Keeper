# 桌面日历那扇窗：图标压着它，日历一整块

**所有者定夺（2026-10-14）：日历待在桌面图标之下，颜色自成一体。**
图标要压在日历上面；日历一整块照画，不按图标挖洞、不留空段。

## 宿主只能是图标层那一扇

本机量过三个爹，问的是同一个问题：把一扇窗挂进去，它画不画。

| 爹 | 画不画原生子窗 | 读数 |
| --- | --- | --- |
| `SHELLDLL_DefView`（图标层） | **画** | 壳自己的 `SysHeader32` 排进图标列表之下，8560 个采样像素**全变**，画面是「名称 / 大小 / 项目类型 / 修改日期」四列 |
| 画布 `WorkerW` | 不画 | 同一扇表头挪进去，0 / 8560 |
| `Progman` | 不画 | 同一扇表头挪进去，0 / 8560 |

**所以宿主只能是图标层**，挂在 `SHELLDLL_DefView` 里、排 `SysListView32` 之下。
那正是「图标压在日历上面」唯一被量到成立的排法。

**画布 `WorkerW` 为什么出局**（这一条最容易记反）：向 `Progman` 发 `0x052C` 之后，
桌面确实会拆出一块满屏可见的画布（`WorkerW 0xD0A70`，排在 `Progman` 子窗堆最底下），
**但它不画 GDI 子窗**。动态壁纸软件挂在那块画布上的不是窗口，是自己绑上去的一套渲染 ——
D3D 设备和交换链。它们的画法我们借不到。

## 画画的不能是引擎自己那一扇窗

引擎日历那一扇挂进壳的父子链之后**不画**。量了三个爹，各配三种逼法：

| 逼法 | 读数 |
| --- | --- |
| 什么都不做（基准） | 0 像素变化 |
| `SW_HIDE` 再 `SW_SHOW`（逼窗口重建） | 0 像素变化 |
| 改小 40 像素再改回来（逼交换链重建） | 0 像素变化 |
| `RedrawWindow(RDW_INVALIDATE\|RDW_UPDATENOW)` + `UpdateWindow` | 0 像素变化 |

挂进图标层、挂进画布、挂进 `Progman`，三种挂法都是 0。
**不是壳拦着**（同一节里原生窗在图标层里画出来了），
**也不是渲染面没跟着走**（三种逼法都试过）。

## 所以：引擎照旧画，画到离屏视口上，像素推进原生子窗

| 一段 | 归谁 |
| --- | --- |
| 日历长什么样、怎么点、怎么选中 | 引擎，**照旧在场景里用真控件搭**（不推翻「界面在编辑器里搭成场景」「界面默认用真控件」那两条） |
| 引擎那一扇窗 | 不再是给人看的那一扇。改成渲染到一块离屏视口上 |
| 像素往哪儿送 | **借壳自己那一扇**（图标层底下那个 `SysHeader32`），补上 `WS_EX_LAYERED`，用 `UpdateLayeredWindow` 推；它挂在 `SHELLDLL_DefView` 里、排 `SysListView32` 之下 |

## 日历那一扇借壳自己那一扇，借来的要还

**产品不自己造那一扇。** 它借图标层底下壳自己放着的那一扇 `SysHeader32`（平时不用的一扇），
补 `WS_EX_LAYERED`、摆到日历那一块、排 `SysListView32` 之下、推进去。

自建那一扇这一条路已经排掉了，四条读数全在研究笔记那一节：自建顶层窗挂进图标层，
`UpdateLayeredWindow` 连推十几发都答真而屏上 0 像素变，同一扇窗抬成顶层就画得出来；
带 `WS_EX_LAYERED` 建子窗 `CreateWindowEx` 当场答 0；不带层叠建出来再补这一位读回是 0、
`UpdateLayeredWindow` 答假、错误码 87。**两条路剩下的差别只有一条：那一扇是壳自己造的。**

**借来的要还。** 不拆（`DestroyWindow` 一发就是拆掉壳的东西），把扩展样式、**窗口样式**、
矩形、可见性、爹和 z 序原样还回去。窗口样式那一项不许漏：编辑态的抬起会把它改成 `WS_POPUP`，
漏了就让壳那一扇留在顶层当浮窗。退出三条路（托盘「退出」、`--seconds`、Esc）都走它。

**放出来那一发真正管用的是 `SWP_SHOWWINDOW`。** `ShowWindow` 那一发发完，可见那一位**一位没动**
（读回来 `|CHILD`，没有 `|VISIBLE`）；`SetWindowPos` 带 `SWP_SHOWWINDOW` 那一发发完立刻答
「可见=True、样式 `|CHILD|VISIBLE`」。**带着这一位，日历才第一次出现在屏上。**


- **必须先发 `0x052C` 桌面才会拆**。不发就找不到画布 —— 之前那一轮量成「没有可挂的壁纸层」就是这么来的，属于**找法错**，不是机器不支持。
- **睡眠唤醒、换分辨率、换 DPI 之后，壳会重建这几层，父子关系会断。** 产品要能自己重新挂上，不能只做一次。
  - 找宿主那一族（`EnumChildWindows` 枚举**全部后代**，不是直接子窗）要按**类名 + 可见 + 满屏**挑，不是按「顶层里没有 `SHELLDLL_DefView` 的那个 `WorkerW`」。后者会挑中别的进程留下的 `170×47` 空壳。

## 点得动靠钩子，不靠窗收鼠标

图标层 `SysListView32` 的矩形是 `(0,0)-(2560,1440)`，铺满整块屏。
挂在它下面的东西**拿不到命中测试** —— `(1700,400)`、`(2100,700)`、`(2400,1100)` 三点命中测试全落到 `SysListView32`。

产品本来就在用全局钩子按坐标判这件事（`src/MouseBridge.cs`），今天真机那一发读数：
点一格日历变了 102 列，而落点按 `WindowFromPoint` 查是 `SysListView32`。
**所以这一族接得住既有机制，但它的可行性挂在钩子那一族上**，改动的头一步要单独验，不能当成已知。

**闸门第三问要图标位置快照，而读失败不许覆盖上一份好的（`DesktopIcons.Keep`）现在归第三问。**
让位那一族撤干净之后这份快照只剩这一个消费方，而它得留下有的是实事：读失败就把上一份好的
扔掉的话，第三问处处答「那一点上有图标」，闸门处处关着，日历格子一个也点不动。
它原来的理由（读失败不许让日历退成整块铺回来）随让位那一族一起作废，那一条不再钉着它。
2026-10-15 由工单 28 定。

## 推进去的像素要按源图自己的 alpha 混

那一扇是层叠窗，而层叠窗最终长什么样由 `UpdateLayeredWindow` 的 `BLENDFUNCTION` 说了算 ——
**不由推过去的字节说了算**。

`BlendFlags = 0` 的意思是「按 `SourceConstantAlpha` 混」：源位图自己的 alpha 通道
**根本不参与**。配上 `SourceConstantAlpha = 0xFF`，就是整块按不透明画。
DIB 是 32 位带 alpha 的、`alpha=94` 的像素照样落成纯黑 —— 整块日历变成一块黑板。

所以定死：**源图是 32 位带 alpha 的 DIB 时，`BlendFlags` 和 `AlphaFormat` 都填
`AC_SRC_ALPHA(1)`，`SourceConstantAlpha` 才留 `0xFF`（那一档它不参与）。**

读数在 `docs/research/desktop-layer-and-window-measurements.md`
「推进去的 alpha 被整块当成 255」那一节。2026-10-17。

**顺带钉住一条读法**：`run.cmd layered` 推的是**不透明纯色**，
所以「19200 / 19200 个像素变」只答得出**推进去了**，**答不出 alpha 有没有被认**。
要问 alpha，得推一张**半透明**的上去。

## 被否掉的路

| 否掉的 | 为什么否 |
| --- | --- |
| **挖洞让位**（日历在图标占的那几列里什么都不画） | 所有者 2026-10-14 推翻：要的是颜色自成一体，不是挖洞。代码已撤 |
| **引擎那一扇窗直接挂进图标层**（排在图标列表之下） | 实测 0 像素变化，三种逼法都试过 |
| **挂进画布 `WorkerW`** | 实测不画原生子窗（0 / 8560）。动态壁纸软件在那块上绑的是自己的 D3D 渲染，借不到 |
| **挂到 `Progman` 上、排图标层之下** | 实测不画原生子窗（0 / 8560） |
| **留在顶层、继续压在图标之上** | 所有者 2026-10-14 推翻：图标要压在日历上面 |
| **`WS_EX_LAYERED` 去掉再挂** | 实测与不去掉逐字相同（MD5 相同），不是层叠样式的事 |
| **产品自己造那一扇层叠子窗再挂进图标层** | 四条读数全在研究笔记：推进去答真而屏上 0 像素变（同一扇抬成顶层就画得出来）、建子窗带 `WS_EX_LAYERED` 当场答 0、不带层叠建出来再补读回是 0 且 `UpdateLayeredWindow` 答假错误码 87。**改成借壳自己那一扇** |

## 代价（写在明处）

1. **离屏读回**。每次画面变了要把视口纹理读回 CPU 再推进原生窗。读回是同步的，所以只在**画面真变了**时做，不每帧做。
2. **原生子窗的 z 序靠不住就得重来**。见上面「壳会拆了重搭」那一条。
3. **改完之后「日历看得见」这件事第一次不归引擎管**。以前引擎画就一定看得见，现在原生窗不出像素就是黑。这个失败模式要能读出来、记进日志。
4. **`UpdateLayeredWindow` 打在图标层里的层叠子窗上，本机量过了（2026-10-16）。** 量到的是：
   壳自己那一扇画得出来，**产品自己造的那一扇画不出来**。差别的根还没查清，
   但修法已经定死在「借壳自己那一扇」这一条上。
5. **借来的那一扇要看它借之前什么样。** explorer 重启前后，壳那一扇的爹不一样
   （重启稳定下来之后是图标层的直接子窗，刚重启那会儿挂在图标列表底下）。判据两种都收。
6. **那一扇被弄过之后就不好量了。** 产品先在一扇壳窗上推过一轮，量具 `layered` 对同一扇再跑
   四发，正档读到 0 / 19200。量「借来的那一扇此刻画不画得出来」之前，要先确认它是干净的。
7. **那一扇的观感由 `BLENDFUNCTION` 决定，不由推过去的字节决定。** alpha 填错一位，
   推过去的字节再对也只出来一块黑板。`Update` 那一发的 blend 三个字段是判据的一部分，
   改它要连屏上那一帧一起量 —— **量具那一族量不到**（它只推不透明纯色）。
