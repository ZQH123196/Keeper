## 遮罩那些窗在启动时就造好，不到点才造

契约说遮罩是**每块屏一扇**的透明置顶窗，而Keeper 可能盖到的每一块，那一扇都在启动时就建好、建了就一直留着，不是到休息那一刻才拿出来。理由是一发实测结果撑得住的：渲染器没法在淡入里冷启动 —— `fadeInMs` 的头几帧会拿去建窗而不是画斜坡，而设计文档 `docs/design/fader-window.md`「一块屏一扇，启动就建好」那一节引的「淡入不许跳」说的正是斜坡。

**代价**：这份成本是常驻的，一辈子在付 —— 底座那一发在 `docs/research/godot-footprint.md`（空项目 2 个进程、199 MB，本机的）。

（这一节是从 README 那句「paid for up front」搬进卡片的：取向本来该住在 ADR 里，以前只在 README 有一份，契约第 76 行那条不变量指过来时没地方落。被否的方案当条没有当场记过，所以这里不补 —— 要哪一条被正式否掉，说一句才写得进去。）

## 桌面日历那扇窗：留在顶层那一族，功能实现参考 wallpaper engine 那一族

> ⚠ **这一节的结论已作废（2026-10-14 所有者定夺）。** 这一节选的是「日历留在顶层、压在图标之上」，
> 那一族现在被否掉了：所有者定了**图标压在日历上面、日历一整块不挖洞**。
> 取向、被否的路、代价全在 `docs/adr/0007-the-calendar-window-is-under-the-icons.md`。
> 这一节下面留着，是因为里面那几段**否掉注入法的实测记录仍然作数** ——
> 「日历整扇看不见」那条读数是真的，只是当时把原因归错了（归成「和契约相反」，实际是引擎那一扇不画）。
> 别把这一节当当前结论读。

**所有者定夺（2026-10-13）：桌面日历的功能实现参考 wallpaper engine。** 那一族是 Lively、Rainmeter 同路。

**这一节 2026-10-13 当天翻过一次案**。上午按那一族的「注入法」写过一版，当天下午的实测把它否掉了。下面写清翻案的理由和读数。

### `WorkerW` 是什么

（这一段是读这一节的前提，不是术语表条目 —— 术语表里没有它，要不要添归所有者。）

Explorer 不把桌面装在一扇窗里。它拆成两扇叠着：上面那扇装**图标**，下面那扇装**壁纸**，类名叫 `WorkerW`。

那扇壁纸窗平时不存在。要它出来，往 `Progman` 发一条未公开消息 `0x052C`，Explorer 自己拆出来。

把自己的窗挂进**壁纸那一扇**，就成了桌面的一部分：压在所有程序窗之下、压在图标之下、不用跟谁抢 z 序。

### 否掉注入法：它和「日历要看得见」直接冲突

`WorkerW` 是把日历挂到**壁纸层**，也就是图标层**之下**。而图标层**不透明**、铺满整块客户区。

**实测（2026-10-13）**：日历挂进 `SHELLDLL_DefView`、排在图标层（`SysListView32`）之下 —— 挂成功了：`WS_CHILD` 补上、`WS_EX_LAYERED | WS_EX_TRANSPARENT` 都在、坐标对、不再抢 z 序。按 Win+D 清场后抓帧：**桌面图标一个没少，日历整扇看不见。**

**所以注入法和契约第 30 行直接相反**。那一行是所有者 2026-10-12 定的：

> 日历留在图标层之上（看得见），**同时**左边让出图标那一列……**两条都要，不是取舍**

上午把「日历整个看不见」读成「这一族不行，缺 `WorkerW`」，那是**把症状当成了原因**。真正的原因是这一族和契约相反，不是缺一扇窗。

### 留着的：顶层 + `WS_EX_LAYERED` 那一族是对的

它一次给齐四件，注入法反而给不齐：

| 要的 | 顶层那一族怎么给的 |
| --- | --- |
| 日历看得见 | 它在 `Progman` 正上方 |
| 图标透过来 | 每像素透明由 DWM 合成，图标从格子底下透过来 |
| 压在别的程序窗之下 | 它插在桌面层正上方 |
| `Win+D` 扫不走 | owner 是 `SHELLDLL_DefView`，Show Desktop 不带它走 |

**四条都实测过**（Win+D 之后抓帧：日历完整可见，`Keeper.exe` 和回收站图标从格子底下透过来，图标一个没少）。

**owner 那一格是 2026-10-13 补验的**：按 Win+D 之后从日历往下走第 1 扇就是 `Progman` —— **日历没有被沉下去**，Show Desktop 不带 owner 是桌面子窗的它走。

### 真正要改的两处，都是判据，不是机制

这一族不需要换机制，要改的是**挑哪一扇**和**拿什么当「摆对了」**。

**一、挑错了一扇**。原来 `DesktopTop()` 从 z 序最顶往下取第一扇壁纸层窗，而实测这台机器上 **12 扇 `WorkerW` 全是不可见的空窗**，位置和图标层没有关系。日历插到其中一扇之上，**鼠标穿过日历之后落不到图标层** —— 症状就是「日历外面能拖图标、日历那一块拖不动」。现在直接认 `Progman`。

**二、判据恒假**。原来问「壁纸层那一扇有没有被翻到我们上面去了」，而动作**恰好就是把日历插到壁纸层某一扇的正上方**，于是判据永远命中刚插进去的那一扇。**一次运行重发 180 次 `SetWindowPos`，收之前和收之后逐字相同。**

现在问「往下走撞不撞得上壁纸层」—— 这一句和动作一致，不可能恒假。

**为什么不写成「往下第一扇壁纸层必须是 `Progman`」**：实测顶层链 300 扇，`Progman` 在**第 181 扇**，12 扇 `WorkerW` 全在**第 66 到 168 扇**，**都比 `Progman` 高**。那一版又变成每秒重插。读数在 `docs/research/desktop-layer-and-window-measurements.md`。

**要问的是「桌面层在不在我下面」，不是「下面那一扇叫什么」。**

### 从 wallpaper engine 那一族借来的那一件

不是它的摆法，是**命中测试**：鼠标每动一下问一次「这一点在不在日历的内容上」，在就让开（`WS_EX_TRANSPARENT`），不在就接着穿。

Keeper 这里是**按坐标判**、而且是**按下和松开才问**（`WH_MOUSE_LL`），不是每动一下问。差别记在这里，下次量的时候对得上。

## 图标位置：产品侧改问 UI Automation

**所有者定夺（2026-10-14）：产品引 UI Automation。** 工单 26 的另外两条路
（放宽「不许跨进程内存」改走 `LVM_GETITEMRECT`、换一条不问位置的走法）因此没走。

**为什么非问位置不可**：日历让开的是**图标实际占的那几列**，判据不许写死像素 ——
用户自己拖图标（最早那份实测记的是「15 颗全在 `x ∈ [0,92]`」，10-14 那一发是
`x ∈ [1302,2138]`）。而鼠标桥那道闸门的第三问问的也是位置，问错读法就是**闸门恒闭、
日历格子一个也点不动**。两件事同一个病根，所以合成一轮做。

**为什么是 UI Automation**：一条问句问完一整层，句子里没有任何跨进程指针，
不需要 `ReadProcessMemory`，也不碰 Explorer 的地址空间。读法抄的是量具那一侧
`src/tools/DebugProbe/Icons.cs`（工单 07 选出来的那一条，本机量通过）。
被否掉的那几族（`LVM_HITTEST` 七档处处答 0、无障碍 `accLocation` 全 `E_INVALIDARG`、
`accNavigate` 崩进程、`IDispatch` 晚绑定第一句就抛）读数在
`docs/research/desktop-layer-and-window-measurements.md`「图标位置读法选型」。

### 代价，写在明处

**产品工程从 `net8.0` 变成 `net8.0-windows` + `<UseWPF>`。** 它要的那一份程序集在
`Microsoft.WindowsDesktop.App` 这个**共用框架**里 —— 系统自带，**不是 NuGet 包**，
所以「不引任何包」那条规矩没被破（引 NuGet 包还要带一串传递依赖，那才叫破）。

**但只改这两行是不够的，这是本节最要紧的一条**：引擎起 C# 那个运行时读的是它自己那份
`GodotPlugins.runtimeconfig.json`，那一份**只列 `Microsoft.NETCore.App`**。
项目自己那份 `Keeper.runtimeconfig.json` 就算列上了 `Microsoft.WindowsDesktop.App`，
进程的程序集列表也是启动那一刻定的 —— 于是 `<UseWPF>` 只够**编译**过，
一到运行期就是 `FileNotFoundException: UIAutomationClient`。所以产品侧要**自己装**
那一族程序集（`DesktopIcons.EnsureAssemblies`）：

1. 从本进程正在跑的那一份共用框架目录按路径装（版本跟着 `System.Private.CoreLib` 走，
   不写死版本号）；
2. 挂 `AssemblyLoadContext.Default.Resolving`：目录里那些程序集互相引用的**版本号对不上**
   （实测 `UIAutomationClient` 8.0.0.0 要 `UIAutomationProvider` **10.0.0.0**，目录里那份是
   8.0.0.0），默认绑定器只肯用更高的版本去满足更低的要，反过来算降级、直接拒；
3. **装程序集那一发不许提到 UI Automation 的类型**：编译器把那些类型记进哪个方法，
   JIT 就在**进那个方法门那一刻**去解析 —— 那一刻还没装，`try` 根本进不去
   （实测就撞在这一下）。所以 `ReadNow` 与 `ReadByUia` 分成两个方法。

**读不在帧里做**：鼠标桥第三问是每帧走的，而这一问一次几十毫秒
（空闲时 60 到 70 毫秒、机器忙时 130 到 180 毫秒；读数在研究文档那一节）。
读排在后台线程上，两次读之间隔 2000 毫秒，
帧里只拿上一次那份快照比矩形（单次 0.03 微秒）。代价：图标被拖过之后让位最多晚两秒跟上。

**重画不跟读的版号走，跟「让开的那几段」走**（工单 27）：版号每读一次涨一次，
拿它当条件等于每两秒整张重下一遍，哪怕屏幕上那几段一个像素都没动。

**一读失败不许覆盖上一份好的**（工单 27）：这一问会瞬时答空（跨进程 COM 抛异常），
而拿到空表就等于把底色铺回图标上面 —— 契约那条「不退成整块铺回来」正是被这一档破掉的。
所以抛异常、答 0 颗、答得比上一份少，三样都沿用上一份好的，只在日志那一句里写清这一读怎么了。
**从没有过好的一份**才轮到写死的下限宽度。

**左键按住的那一段冻结**（工单 27）：拖图标时 UI Automation 答的矩形跟着光标走，
于是让位竖条每两秒跳一次、今天那格的蓝边落进去就消失。按下那一刻冻结、松开那一刻解冻
（判据走 `Activity` 已有的那一个钩子出口，不新增钩子）。**冻结只管读数，不管闸门**
（工单 27 第二轮，2026-10-14）：闸门第三问在钩子那一刻答、跟着那一发排队，
按下和松开配成对。原先那一版还让「按住」等于「读不可信」、闸门整条闭着 ——
而闸门答在抽干那一刻，按下被丢掉、松开被喂进去，控件收到没有配对的那一对，
**日历格子一个也点不动**（真机读数：点 22 那一格前后日历那块一个像素都没变）。
契约「无感」第 3 条要的是「**落在图标上**时只有图标响应」——
落在图标上那一点闸门仍然闭着，而按住本身不构成闭门的理由。

**读不出来那一档走写死的下限宽度（`DesktopIcons.FloorWidthPx`），不退成 0** ——
退成 0 就是整块铺回来，正是要修的那个症状。

## 置顶那一位不赋引擎旗标，落定走 `HWND_NOTOPMOST`

`AlwaysOnTop` 在窗已经显示之后再赋，引擎会把 `WS_VISIBLE` 清掉、遮罩整个消失 —— 赋成 `false` 和赋成它本来就有的 `true` 都一样，所以那不是「设一个属性」而是「拆一扇窗」。淡入那一段必须顶到最上面；`stayOnTopAfterLanding` 关掉时，落定之后不赖着，要切去别的程序看一眼，那个窗口就该盖得住它。落定这一发因此走 `SetWindowPos(HWND_NOTOPMOST, …|SWP_NOACTIVATE)`，那本来就是「非置顶栈顶」。

**2026-10-29 所有者定夺推翻默认值**：休息时段始终盖上，Alt+Tab 切不走 —— `stayOnTopAfterLanding` 默认改成 **true**，上面那一发只在它关掉时才走。

配套那条**只归遮罩**：它的样式位在别的一切之前一次设完、之后不碰 —— 那一发读到「爹掉了」出自设完置顶又去改标题。挂进壁纸的那扇日历窗、测量程序抬起那一段改扩展样式是设计的一部分，不归这条管。

## 鼠标桥默认不喂

2026-09-26 那一发：桥整个关掉，一发真实注入的点击仍然作为一次完整的按下 + 松开到达那扇嵌进壁纸的窗 —— OS 自己会跨过那条进程边界投鼠标消息；再拿 `WH_MOUSE_LL` 把同一点喂进去，就是**一次点击数两下**。所以默认不喂，`--feed` 是留着复测的开关，「默认不喂」那一句住在 `GLOSSARY.md` 的「鼠标桥」条。

这一旗留着而不是把桥拆掉，缘故是一条范围：那一发只在这台机器、这一个 `SHELLDLL_DefView` 挂在 `Progman` 底下的形状上量过（没有 `WorkerW` sibling）。换一台真点不动，拧开这一旗就是 `--feed` 那一发。

桥当年要解决的问题（一次双击该由 shell 判）现在在这一侧判：那扇窗不被委托，它自己盯第二次按下然后抬窗。

## 穿透走 `WS_EX_LAYERED | WS_EX_TRANSPARENT` 那两位，判定不能只看 `WindowFromPoint`

引擎在册的每一条 passthrough 路线都单量过一发（矩阵在 `src/Probe.cs`）。**2026-10-11 晚更正**：这一节的结论当年量错了，错在**量的是进程内口径**。

**原来写的**：答「通」的有两条（引擎的 `Window.MousePassthrough`、手设 `WS_EX_TRANSPARENT`），生产走引擎那一条；判定只看 `WindowFromPoint` 回谁。

**为什么那是假绿**：引擎那条走的是 `WM_NCHITTEST`，而 `HTTRANSPARENT` **只跨同一个线程**。遮罩答「这一点不是我的」是对的，**同一线程里下面那扇收得到，跨进程收不到——那一发就没了**。而当年两处判据都答不到这一句：

1. `WindowFromPoint` 从**进程内**问时会跳过答 -1 的那一扇，所以它一路读绿；
2. 接收方（`ClickTarget`）也在**测量程序自己这个进程里**，而同线程的穿透是真的，所以它也读绿。

**新取向**：铺满那一扇手动补上 `WS_EX_LAYERED | WS_EX_TRANSPARENT`（`Fader.ArmClickThrough`，`Show()` 之后一次，之后不碰）。**引擎旗标留着**——它不冲突，而「样式位一次设完」那条规矩说引擎旗标在构造里一次设完最省事。

**为什么必须伸手到 Win32**：根 `AGENTS.md`「引擎能做的就用引擎，够不着的才伸到 Win32」里**够不着的那一档**。引擎没有第二条 passthrough 路，而 `WM_NCHITTEST` 这一条跨不到别的程序。

**判定口径**：**进程内的 `WindowFromPoint` 不能当穿透的证据**（它问的是命中测试，而命中测试不是点击到不到）。跨进程那一头只能由两进程那一发答（`Probe --passthrough-target --selfclick --plain` + `FadeRun --hold`）。自检里留的那一条是**必要条件**：那两位扩展样式位还在不在（`FadeRun.ClickThroughBitsHeld`）—— 位没了则一定不通，位在不一定通。

**否掉的**：多边形那几条 `WindowSetMousePassthrough` 路线（答「不通」，而且那个多边形是**收事件**的区域，空数组等于关掉）；只发 `HWND_TOP` 来把自己挪出置顶那一叠（那一位是 z 序管的，改样式位没读回来说明它不认）。

## ~~清单和那颗钮搬进第二扇窗~~ → 点得到的那几块交给钩子按坐标判

**这一节 2026-10-10 翻案。** 下面是退休的取向，留在原地是为了说清它为什么退休、新的那一节是什么。

遮罩那一扇永远 click-through。收鼠标的是**点击窗**（`src/FaderClickWindow.cs`）：每块屏第二扇窗，只罩住休息清单那几行和「提前结束休息」那颗钮。

**为什么不能一扇窗两档**：上面那一节量过的结论直接搬过来 —— 在册的每一条 passthrough 路线，答「通」的只有两条，两条都是**整扇窗**一个开关。Windows 的 `WM_NCHITTEST` 那条路（引擎的多边形就是它）只跨**同一个线程**的窗，跨不到别的程序；而 Godot 文档自己写着，Windows 上多边形之外**不画** —— 用它会把整层遮罩削掉。两条死路一堵，「清单点得动」和「底下照常用」就只剩拆窗。

**为什么点不落到控件上，落到坐标上**：点击窗里没有控件，只有一个 `GuiInput`，把点交回 `Fader.Route` 按控件**摆完版之后的矩形**判。所以「点字、点方块、点中间那条缝都算勾这一行」仍然成立，走的那条路从引擎的 GUI 拾取换成了按矩形判 —— 判据还是引擎摆出来的那个矩形，不是手算的布局。

**代价有三条，都写在明处**：

1. 「提前结束休息」从中间页脚搬到了清单一列下面（`FaderContent.tscn`）。它在侧面而清单在屏幕正中下方时，点击窗要同时罩住两处就得连中间那大半块屏一起罩住 —— 罩进去的每一像素都是底下点不到的像素。搬过来是为了让「点得到的东西」连成一小块。
2. 点击窗的矩形要在**排版跑完之后**才量得到，所以换步那一发等三帧（`Fader.ReportExit`）才举它，落定那一发直接举。
3. 收起点击窗走 `ShowWindow(SW_HIDE)`，不走 `Window.Hide()` —— 后者从 C# 什么都不做（`CODING_STANDARDS.md`「代码级规矩」那一条量过）。

**没量的**：点击窗真正罩住多大、底下那些像素是不是真能点到底下的程序 —— headless 的 DisplayServer 报的屏是 1×1，量不了；归非 headless 那一发（欠账工单里那一条）。

### 翻案：那一扇窗本身就是「占住鼠标」（2026-10-10）

**所有者定夺「永远都不能抢鼠标，这是 bug」。** 点击窗和铺满那扇的区别只是**罩多大** —— 它罩进去的每一像素，底下的程序就点不到那一像素。那不是「把一块小地方借给我」，那还是占住，只是占得小。

**新取向**：

- **铺满那一扇一辈子 click-through**，一步一步都是 —— 包括休息流程里写着「接鼠标」的那一步。
- **「点得到的那几块」不再有窗**。它是**一块矩形**（`src/ClickRegion.cs`，并矩形的正本，编辑器和产品调同一段算术），交给本来就装着的 `WH_MOUSE_LL` **按坐标判**（`Activity.MouseSwallower`）：落在那一块里的**左键按下**返回非零，系统不把它递给任何窗。
- **「返回非零 = 真的吃掉」是量出来的**，不是推的：接收方那一下真的到不了（实测结果在 `docs/research/desktop-layer-and-window-measurements.md`「钩子能不能吃掉那一档」那一节，三档读数原文）。
- **委托只许答「吃 / 不吃」**，不许在回调里干活 —— 那个回调挂在**全机输入的同步路径**上。勾清单那一下走 `App._Process` 的下一帧。
- 判定只认**左键按下**。拖动、滚轮、双击的第二下各走各的老规矩。

**新代价，写在明处**：**勾清单那一下也点到底下的程序**。这是明面上的代价，不是 bug —— 要「勾清单不点到底下」，就得保留那一扇收鼠标的窗，而那正是被否掉的那一条。两者只能要一个。

**为什么不用上面那一节已经量过的 `WM_NCHITTEST`**：它跨不到别的进程，而要「底下的程序照常收得到」恰恰要求那一发**走到别的进程去** —— 钩子返回非零是**在递交之前**掐掉，而 `WM_NCHITTEST` 是**递交之后**问「这归谁」。问一个你已经递出去的东西，答什么都不影响它已经落到别人那儿。这是两条路的根本差别，不是快慢。

**否掉的**：上面那三条代价里第 3 条（`ShowWindow(SW_HIDE)` 收起点击窗）随那一扇窗一起退休；第 1 条（那颗钮搬到清单一列下面）**留着** —— 矩形算的是点得到的那几颗控件，控件离得越近、算出来的块越小，不搬它块就大。第 2 条（等三帧再量）**留着**，那是排版跑完才量得到真值，与有没有窗无关。

## Esc 收尾数全局键盘钩子，不翻 `FocusMode`

遮罩收了鼠标的那一段里要「按 Esc 就收尾」。另一条路是把窗改成能拿焦点（翻 `FocusMode`），但那要碰「换档不碰窗：不闪、不重举」这一条 —— 而换档那一刻正是 `Enter()`。所以数本来就装着的 `WH_KEYBOARD_LL`。

**代价**：算的是全局那一下 —— 收了鼠标的那一段里，任何人按 Esc 都收尾，不看焦点在谁那里。还有一件没量：翻 `FocusMode` 会不会像 `AlwaysOnTop` 那样把窗整个藏掉 —— 选了钩子就不必去量，那是**没做的对照**，不是已知风险。

## 一颗图标，一个进程：内核持有的具名互斥体

再启动一次不该多出第二颗托盘图标：第二发把「有人又点了一次」递给已经在跑的那一发就退掉自己（「让路」），接到的那一发露面 —— 开设置窗（这程序没有别的主窗，那是最接近的东西），已经开着就把它提到前面。要并行量两发用 `--anyway` 明说，那时屏幕上就是两颗。

**选互斥体而不是 PID 锁文件的理由**：开发时强杀不算事故 —— `taskkill` / `Stop-Process -Force` 杀掉的那一发和干净退出一样立刻放锁，下一发起来不需要先重启什么把锁清掉；锁文件会留在盘上，于是「重启没反应」，而那些残留 PID 隔几天还可能被系统分给别的程序。名字必须带 `Local\` 前缀（裸名字 .NET 会当 `Global\`，一个 RDP 会话就会把另一个会话挡住）。
